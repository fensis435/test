## 📝 Webシステム設計メモ：NGINX auth_request を活用したID変換と負荷分散アーキテクチャ## 1. auth_request の基本概要と仕組み
auth_request とは、主にNGINXで利用される認証・認可の制御機能（ディレクティブ）である。クライアントからのリクエストがメインのバックエンド（アプリケーション）に到達する前に、内部の認証サーバー（auth_service）へ事前問い合わせ（サブリクエスト）を行い、アクセスの可否を判定する。
## ■ 基本的な挙動のルール

   1. HTTPステータスコードによる判定:
   * auth_service が 200 OK を返した場合 ➔ 認証成功。メインのバックエンドへリクエストを転送する。
      * 401 Unauthorized または 403 Forbidden を返した場合 ➔ 認証失敗。NGINXがその場でアクセスを遮断し、エラーを返す。
   2. データのやり取りは「HTTPレスポンスヘッダ」で行う:
   * NGINXは auth_service が返す「レスポンスの本文（JSONなど）」を解析できない。
      * そのため、データの引き継ぎには必ず HTTPレスポンスヘッダ を利用する必要がある。
   
------------------------------
## 2. ランダムIDから内部IDへの変換プロセス
クライアントが提示した外部用の「ランダムID」を、セキュリティやデータ整合性のために「内部用ID」に書き換えてバックエンドへ渡す処理の具体的な流れ。
## ■ 処理シーケンス

   1. リクエスト受信: クライアントが X-Random-ID: rand123 をヘッダに付与してNGINXにアクセスする。
   2. 認証転送: NGINXが auth_service へヘッダをそのまま転送する。
   3. IDの解決と返却: auth_service（HTTPサーバーで駆動するアプリ）がDBやRedisを参照し、ランダムIDに対応する内部ID（例: int9999）を特定。レスポンスヘッダ X-Internal-ID: int9999 を付与し、200 OK を返却する。
   4. 変数の上書きとバックエンド転送: NGINXが auth_request_set を用いてヘッダの値を抽出。本来のバックエンドへ送るヘッダ（例: X-User-ID）を内部IDに書き換えて proxy_pass で転送する。

## ■ NGINX設定ファイルの記述例

server {
    listen 80;

    # メインのAPI受け口
    location /api/v1/ {
        # 1. 認証用サブリクエストの実行
        auth_request /auth_check;

        # 2. auth_serviceが返したヘッダ「X-Internal-ID」を取得し変数に格納
        auth_request_set $internal_id $upstream_http_x_internal_id;

        # 3. バックエンドへ転送するヘッダを内部用IDに書き換え
        proxy_set_header X-User-ID $internal_id;

        # 4. バックエンドサーバーへ転送
        proxy_pass http://backend_app_cluster;
    }

    # 内部的な認証問い合わせ先の設定
    location = /auth_check {
        internal; # 外部からの直接アクセスを禁止
        proxy_pass http://auth_service_app;

        # 【負荷・不要データ対策】不要なヘッダをクリアし、必要なものだけ送る場合
        # proxy_pass_request_headers off;
        # proxy_set_header X-Random-ID $http_x_random_id;

        # ボディデータの転送をオフにして軽量化
        proxy_pass_request_body off;
        proxy_set_header Content-Length "";
    }
}

## 3. 認証サーバー（auth_service）の実装要件
auth_service は特別なミドルウェアではなく、任意の言語（Go、Node.js、Python等）で記述された「普通のHTTPサーバー（Webアプリケーション）」として開発する。
## ■ アプリケーションコードの実装イメージ（Node.js / Express例）

const express = require('express');const app = express();

app.get('/auth_check', (req, res) => {
    // 1. NGINXから引き継いだヘッダの読み取り
    const randomId = req.headers['x-random-id'];

    // 2. 高速なデータストア（Redis等）から内部IDを検索 (擬似コード)
    const internalId = redisClient.getSync(randomId); 

    if (internalId) {
        // 3. 成功時：レスポンスヘッダに成果物を乗せて 200 OK
        res.setHeader('X-Internal-ID', internalId);
        res.sendStatus(200); 
    } else {
        // 4. 失敗時：401を返してNGINX側でブロックさせる
        res.sendStatus(401);
    }
});

app.listen(8080);

## 4. ボトルネックの回避と「王道」の負荷対策
すべてのアクセスに対して毎回 auth_service やその奥のDBへの問い合わせが発生すると、認証周りがシステム全体のボトルネック（パンクの原因）となる。これを防ぐための階層的な負荷対策。
## ① ルーティングによる対象の絞り込み
Webサイトのアクセスの大半（7〜8割）を占める画像、CSS、JavaScript、HTMLなどの「静的データ」は、最初から auth_request の対象外（Locationブロックを分ける）にする。認証が必要な動的API（全体の2〜3割）だけに適用することで、負荷を劇的に削減する。
## ② NGINXによる「手前」での静的データ即時返却
末端のアプリケーションサーバーまで静的データを取りに行かせず、最前線のNGINXサーバーのローカルディスク内に静的ファイルを最初から配置（あるいは事前生成）しておく。NGINXがアプリケーションを介さず直接ファイルを返すため、アプリケーションのCPU・メモリ負荷がゼロになる。
## ③ CDN（最前線）の導入によるキャッシュ戦略
さらに手前に CDN（CloudFrontやCloudflareなど） を配置し、あらかじめ作成しておいた静的データを最前線で完全にキャッシュさせる。

* 静的データ: CDNで100%ヒットしてその場で返却されるため、NGINXにもアプリにもアクセスが届かない（負荷ゼロ）。
* 動的API: CDNを通過してNGINXへ到達。NGINX上の auth_request ➔ auth_service（Redis等の高速データストアと連携）のルートで超軽量・高速に処理される。
