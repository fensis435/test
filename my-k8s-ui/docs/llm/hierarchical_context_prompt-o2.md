後半の質問から答えると、

**「AI専用ナレッジベース = コードそのもの」にはならない。**

ただし、目的によっては80〜95%くらいの効果を出せることがある。

---

## コード入力と同じ効果は得られない理由

例えば実コードに

```python
def calculate_discount(user, order):
    ...
```

が1000箇所あったとする。

ナレッジベースには

```text
割引計算は DiscountService が担当する
VIPユーザーは追加割引がある
```

しか残らない。

するとAIは

* ビジネスルールは理解できる
* 実装詳細は分からない
* 関数名や引数までは分からない

という状態になる。

つまり

### 得意

* 設計相談
* 機能追加方針
* リファクタ方針
* バグ調査の当たり付け

### 苦手

* ピンポイント修正
* 実コード生成
* シグネチャ参照
* 正確な依存関係

---

## 逆にナレッジベースの強み

巨大コードベースでは

```text
100万行
↓
全部投入
↓
コンテキスト圧迫
```

よりも

```text
100万行
↓
AI_CONTEXT
↓
必要箇所だけコード取得
```

の方が賢い。

実際、最近のAIコーディングツールはほぼこの思想。

---

# 階層化プロンプト

私なら一発で巨大な要約を作らせず、

まずインデックスを作る。

---

## Step1

```text
このリポジトリ全体を分析してください。

以下のMarkdownファイル群として
AI向けドキュメント体系を設計してください。

出力形式:

# Recommended Documents

- PROJECT_OVERVIEW.md
- ARCHITECTURE.md
- DATABASE.md
...

各ファイルについて

- 目的
- 想定サイズ
- 含める内容

を説明してください。

トークン効率を最優先してください。
```

---

例えば

```text
PROJECT_OVERVIEW.md
全体像

ARCHITECTURE.md
システム構造

DOMAIN_RULES.md
業務ルール

DATABASE.md
DB設計

API.md
API仕様

FRONTEND.md
UI構造

BACKEND.md
サーバ構造
```

みたいな設計を出させる。

---

## Step2

次に各ファイルを個別生成。

### PROJECT_OVERVIEW

```text
PROJECT_OVERVIEW.md を作成してください。

対象読者は
このプロジェクトを知らない別のLLMです。

実装詳細ではなく、

- システム目的
- ユーザー像
- 機能一覧
- 技術スタック

を中心にまとめてください。

8000トークン以内。
```

---

### ARCHITECTURE

```text
ARCHITECTURE.md を作成してください。

以下を含めてください。

- レイヤ構成
- ディレクトリ責務
- モジュール依存
- データフロー
- イベントフロー

後続LLMが設計変更できるレベルで。
```

---

### DATABASE

```text
DATABASE.md を作成してください。

以下を含めてください。

- 全テーブル一覧
- 主キー
- 外部キー
- 重要制約
- ER関係

SQL定義の転載ではなく
概念モデルとしてまとめてください。
```

---

### DOMAIN_RULES

これがかなり重要。

```text
DOMAIN_RULES.md を作成してください。

コードベースから推測できる
業務ルールを抽出してください。

例:

- 注文キャンセル条件
- 権限制御
- 課金ロジック
- 承認フロー

コードではなく
ルールとして記述してください。
```

---

## Step3

最後に総合インデックス

```text
AI_CONTEXT.md を作成してください。

各ドキュメントの要約と
参照順序を記載してください。

初めて読むLLMが
どのファイルから読むべきかを説明してください。

内容を重複させないでください。
```

## さらに実務的なプロンプト

私はむしろこう頼むと思う。

```text
このコードベースについて
別のLLMが最短時間で戦力化できる
知識ベースを作成してください。

目的は要約ではありません。

後続LLMが

- 機能追加
- バグ修正
- リファクタ
- 設計変更

を安全に行うための情報を抽出してください。

重要:

実装詳細よりも

- なぜそう設計されているか
- 何を壊してはいけないか
- どこが複雑か

を優先してください。
```

これが意外と重要で、AIは放っておくと「コードの説明書」を作る。

でも本当に欲しいのは、

> このシステムで絶対に壊してはいけない部分は何か

という保守者向け知識なんだ。

その情報は、生のコードを何十万行読ませても毎回再発見させる必要があるけれど、一度ナレッジベース化すると高性能モデルに何度も使い回せる。だから「コードと同じ効果」ではないが、「開発作業に必要な知識の圧縮」という観点では非常にコストパフォーマンスが高い。
