ここまでの会話を、新しいチャットで開発を継続するための「引き継ぎ資料」に整理してください。

目的は、次のチャットのLLMが、これまでの会話を直接参照できなくても、この資料を読むことで現在のシステムを理解し、開発を継続できるようにすることです。

単なる会話の要約ではなく、これまでのあなたの回答に含まれているシステムに関する理解・分析・判断を抽出してください。

以下の構成でMarkdownとして作成してください。

# 1. システム概要

* このソフトウェアが何をするものか
* 主な利用者・利用目的
* システム全体の役割

# 2. システム構成

主要なコンポーネント、モジュール、外部サービス、DBなどを整理してください。

可能であればMermaidで構成図を作成してください。

# 3. 主要な処理フロー

主要なユースケースごとに、処理がどのように流れるのかを整理してください。

可能であればMermaidのsequenceDiagramまたはflowchartを使用してください。

# 4. コンポーネント・モジュールの役割

各主要ファイル、クラス、モジュールについて、
「何をするものなのか」という観点で整理してください。

# 5. データの流れ

重要なデータが、
どこから入り、どのように変換され、どこへ渡され、どこに保存されるのかを整理してください。

# 6. 重要な仕様・制約

今後の修正で壊してはいけない仕様、互換性、外部システムとの取り決めなどを整理してください。

# 7. これまでの意思決定

開発中に検討された案のうち、今後の実装判断に影響するものを整理してください。

特に、

* 採用した案
* 却下した案
* 却下した理由
  を明記してください。

# 8. 現在の実装状態

現在どこまで実装・修正されているかを整理してください。

# 9. 既知の問題・未解決事項

現在認識されている問題や、まだ判断されていない事項を整理してください。

# 10. 今後の開発で注意すべき事項

これまでの会話から、次のLLMが誤解しやすそうな点や、勝手に変更してはいけない点を整理してください。

## 重要なルール

* 元の会話を逐語的に要約する必要はありません。
* ユーザーとLLMの発言を時系列に並べる必要もありません。
* 現在のシステムを理解するために必要な情報を抽出してください。
* 同じ内容が複数回出てくる場合は統合してください。
* 途中で方針が変更された場合は、最終的な方針と、変更理由を残してください。
* 却下された案でも、今後のLLMが再提案しそうなものは記録してください。
* 会話から確実に分からないことは推測で補完せず、「不明」「要確認」と明記してください。
* コードそのものを大量に転載する必要はありません。
* ファイル名、クラス名、関数名など、今後ソースコードを参照するために有用な識別子は残してください。
* 特に「なぜ現在の構成になっているのか」という理由を可能な限り残してください。

最後に、この資料だけを新しいチャットに渡した場合に、現在のシステムを理解するうえで不足している情報があれば、「不足情報」として列挙してください。
