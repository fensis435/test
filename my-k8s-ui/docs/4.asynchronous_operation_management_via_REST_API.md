# REST API 経由での非同期操作管理：ステータス＆進捗の設計パターン

非同期ジョブ（インストール／起動／停止など）を REST API で扱う際、「処理が終わったか」「どれだけ進んでいるか」をクライアントが取得できるようにするには、以下のような設計が一般的です。

---

## 1. 専用テーブル（Operations テーブル）を用意する

### テーブル設計例

| カラム名        | 型         | 説明                                                       |
|---------------|-----------|----------------------------------------------------------|
| id            | UUID      | プライマリキー（`operationId`）                                    |
| app_id        | UUID      | 対象リソース（App）への外部キー                                     |
| action        | string    | `install` / `start` / `stop` / `restart` / `uninstall`         |
| status        | string    | `pending` / `processing` / `completed` / `failed`          |
| progress      | integer   | 0?100 のパーセンテージ                                       |
| error_message | text      | 失敗時のエラーメッセージ                                         |
| meta          | jsonb     | 任意のメタ情報（例：helm リリース名や namespace など）               |
| created_at    | timestamp | 作成時刻                                                     |
| updated_at    | timestamp | 最終更新時刻                                                 |

### 主な API エンドポイント

1. POST /apps/:id/start  
   - レスポンス: `{ operationId: "..." }`  
2. GET /operations/:operationId  
   - レスポンス:  
     ```json
     {
       "operationId": "...",
       "appId": "...",
       "action": "start",
       "status": "processing",
       "progress": 45
     }
     ```
3. オプション：GET /apps/:id/operations で履歴一覧を返却

### フロー

1. リクエスト受け付け時に `Operations` レコードを `pending` で作成  
2. バックグラウンドジョブ（ActiveJob/Scheduler）が実行を開始するときに `status: processing` & `progress: 0`  
3. ジョブ中、進捗に応じて `progress` を更新  
4. 正常終了時に `status: completed` & `progress: 100`  
5. 異常時に `status: failed` & `error_message` をセット

クライアントは `GET /operations/:id` をポーリングしてステータスと進捗を取得します。

---

## 2. Resource 側にフィールドを直接持たせるパターン

アプリ（`App`）テーブルに状態情報を持たせ、以下のようにフィールドを拡張します。

```ruby
# apps テーブルマイグレーション例
add_column :apps, :status,  :string, default: 'stopped'
add_column :apps, :progress, :integer, default: 0
```

- Pros：テーブル数が増えずシンプル  
- Cons：同時に複数操作の履歴を持てない／開始?完了の過程は掴みにくい

REST では `GET /apps/:id` のレスポンスに `status` と `progress` を含め、変更をポーリングします。

---

## 3. プッシュ通知（SSE / WebSocket）併用

ポーリングではなくサーバープッシュを使いたい場合：

- **SSE（Server-Sent Events）**  
  - Rails なら `ActionController::Live` で `/operations/:id/stream` エンドポイントを実装  
- **WebSocket（ActionCable）**  
  - `OperationChannel` を用意し、ジョブ内で `ActionCable.server.broadcast`  

これによりクライアント側はリアルタイムに更新を受け取れます。

## 4. 実装イメージ：Rails + ActiveJob + Operations テーブル

```ruby
# app/models/operation.rb
class Operation < ApplicationRecord
  belongs_to :app
  enum status: { pending: 0, processing: 1, completed: 2, failed: 3 }
end
```

```ruby
# app/controllers/apps_controller.rb
def start
  op = Operation.create!(app: @app, action: 'start', status: :pending, progress: 0)
  StartJob.perform_later(op.id)
  render json: { operationId: op.id }, status: :accepted
end
```

```ruby
# app/jobs/start_job.rb
class StartJob < ApplicationJob
  def perform(op_id)
    op = Operation.find(op_id)
    op.processing!
    op.update!(progress: 0)

    # 例：K8s 操作を実行
    perform_k8s_start(op.app) do |step, total|
      percent = (step.to_f / total * 100).to_i
      op.update!(progress: percent)
    end

    op.update!(status: :completed, progress: 100)
  rescue => e
    op.update!(status: :failed, error_message: e.message)
  end
end
```

```ruby
# app/controllers/operations_controller.rb
def show
  op = Operation.find(params[:id])
  render json: {
    operationId:  op.id,
    appId:        op.app_id,
    action:       op.action,
    status:       op.status,
    progress:     op.progress,
    errorMessage: op.error_message
  }
end
```

---

## 5. クライアントの扱い方

1. 操作リクエスト（例：POST /apps/123/start）  
2. レスポンスの `operationId` を受け取る  
3. 一定間隔（例：1?2 秒）で `GET /operations/:operationId` を呼び、`status`/`progress` を取得  
4. `status: completed|failed` になったらポーリング停止して結果を反映

---

### まとめ

- **専用テーブル** を用意するパターンが最も柔軟で履歴管理にも向く  
- 単一操作なら **Resource 側フィールド** に格納してシンプルに  
- ポーリング＋プッシュ通知（SSE/WebSocket）を組み合わせると UX 向上  
- Rails ActiveJob から `Operation` レコードを逐次更新し、REST API で取得できるようにすることで、クライアントは簡単に終了判定と進捗を取得できます。
