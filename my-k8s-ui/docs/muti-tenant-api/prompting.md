LLMに一度にすべてのコードを書かせるのではなく、**6つの工程に分け、各工程で成果物を作り、その成果物を次の工程のインプットにする**方法をおすすめします。

特に重要なのは、既存システムのソースコードから、セッション・タブID・テナントアクセス用token・Redisの関係を正確に把握してから設計することです。ここを曖昧にしたまま実装に進むと、見た目は動いても、テナント間の状態が混ざるといった問題が起こり得ます。

以下に、**各工程の目的、インプット、具体的なプロンプト、成果物、次工程への引き継ぎ方**をまとめます。プロンプトはそのままコピーして使えるようにしています。

# 全体像：6工程で進める

今回のシステムの前提は、次のように整理します。

* 既存システムにはサーバ側セッションがあり、セッションIDとタブIDで状態を識別する。
* タブIDは、1ユーザー・1セッションで複数テナントを同時操作するために使用される。
* テナントアクセス用APIには、PATHにテナントアクセス用tokenが含まれる。
* テナントアクセス用tokenに関連する情報は、既存システムのRedisでも管理される。
* 新API層ではAPI専用ユーザーを使用し、既存システム固有のユーザー・セッション・タブID・認証方式を呼び出し元に隠蔽する。
* 呼び出し元は、新APIを通じてテナントを指定する。既存システムの内部識別子は指定しない。
* 新API層はRedisを利用し、新API用tokenと内部の操作コンテキストを対応付ける。
* テナントごとの操作状態はタブIDで分離する。

なお、API専用ユーザーのセッションを複数の呼び出し元で共有するかどうかや、テナントアクセス用tokenの具体的なライフサイクルなどは、これから調査・設計する事項です。プロンプトでも、これらを確定事項として扱わないようにします。

## 工程一覧

| 工程 | 内容              | 主なインプット                    | 成果物                 |
| -- | --------------- | -------------------------- | ------------------- |
| 1  | 既存システムの解析       | 既存API・セッション・Redis関連のソースコード | 既存システム分析レポート        |
| 2  | 状態遷移・依存関係の整理    | 工程1のレポート、関連ソースコード          | 状態遷移図、API依存関係図      |
| 3  | 新API層の設計        | 工程1・2の成果物、業務要件             | API仕様書、Redis設計書     |
| 4  | エラー・競合・セキュリティ設計 | 工程1〜3の成果物                  | 異常系仕様、競合対策、セキュリティ設計 |
| 5  | 実装計画            | 工程1〜4の成果物、既存プロジェクトの構成      | 実装タスク、ファイル構成、テスト計画  |
| 6  | 実装・検証           | 承認済み設計、実装計画、既存プロジェクト       | 実装コード、テストコード、検証結果   |

各工程で重要なのは、次の工程に進む前に成果物をレビューすることです。**工程1の分析結果をレビューせずに、工程2以降へ進まない**ことを特におすすめします。

# 工程1：既存システムのソースコード解析

## 目的

既存システムが実際にどのように動いているかを把握します。

この段階では、新APIの設計や実装は行いません。

特に、次の関係を明らかにします。

1. API専用ユーザーのログインとセッション生成
2. セッションIDとタブIDの管理
3. タブIDとテナント操作状態の対応関係
4. テナントアクセス用tokenの発行・使用・失効
5. テナントアクセス用Redisの構造
6. 既存API間の依存関係
7. セッションやタブの終了処理

## インプット

最初からリポジトリ全体を一度に読み込ませる必要はありません。

まず、以下のファイルやディレクトリを用意します。

| インプット      | 内容                            | 優先度 |
| ---------- | ----------------------------- | --- |
| リポジトリ構成    | ディレクトリ一覧、主要モジュール              | 必須  |
| API定義      | Controller、Router、OpenAPI定義など | 必須  |
| 認証・セッション処理 | ログイン、セッション生成・取得・破棄            | 必須  |
| タブ管理処理     | タブIDの生成、登録、参照                 | 必須  |
| テナントアクセス処理 | テナントアクセス開始、token発行など          | 必須  |
| Redis関連コード | キー生成、読み書き、TTL、削除              | 必須  |
| ミドルウェア     | 認証、認可、Cookie、ヘッダー処理           | 重要  |
| 既存テスト      | API・セッション・Redis関連のテスト         | 重要  |
| 設定ファイル     | Redis接続設定、セッション設定など           | 重要  |

設定ファイルには秘密情報が含まれる場合があります。パスワード、APIキー、実際のtoken、個人情報などは除去してから入力してください。

### ソースコードの量が多い場合

次の順序で解析すると効率的です。

1. リポジトリ構成とAPI一覧
2. 認証・セッション管理

4. テナントアクセスとRedis
5. 対象となる業務API
6. 関連テスト

各段階で分析レポートを更新し、最後に統合します。

## プロンプト1-B：セッション・タブ・テナントアクセスの詳細解析

# 工程2：状態遷移とAPI依存関係の整理

## 目的

工程1で調査した内容を、API呼び出しの順序と状態遷移として整理します。

この工程は重要です。API単体の仕様が分かっていても、API間の依存関係が分からなければ、正しい呼び出し順序を実装できないからです。

例えば、次のような処理順序が存在するかもしれません。

```text
API専用ユーザーのログイン
    ↓
セッションの確立
    ↓
タブIDの作成
    ↓
テナントアクセス用tokenの取得
    ↓
テナントアクセス用状態の確立
    ↓
業務APIの呼び出し
    ↓
タブの終了
```

これは仮の例です。実際の順序は工程1の調査結果から確定します。

## インプット

1. 工程1-Aのリポジトリ分析レポート
2. 工程1-Bの詳細解析レポート
3. 関連するソースコード
4. 関連する既存テスト

## プロンプト2-A：API依存関係と状態遷移図の作成

あなたは、既存システムのAPI間の依存関係と状態遷移を分析するシステムアーキテクトです。

工程1で作成した分析レポートと、関連する既存ソースコードを使って、既存システムの状態遷移とAPI呼び出し順序を整理してください。

まだ新APIの実装コードは作成しないでください。

## 前提

既存システムでは、API専用ユーザーを利用する新API層を将来的に追加します。

新API層は、既存システムのユーザー・セッション・タブID・テナントアクセス用tokenを呼び出し元から隠蔽する予定です。

1つの既存セッション内で複数のタブIDを使い分け、複数テナントを同時に操作することが要件です。

## タスク1：API依存関係

各APIについて、次を整理してください。

* 呼び出し前に必要な状態
* 前提として呼び出す必要があるAPI
* APIの実行で作成・変更・削除される状態
* 後続で呼び出せるAPI
* エラー時に残る状態
* リトライ可能性

APIの依存関係を図で示してください。

## タスク2：状態遷移

少なくとも次の状態を調査してください。

* 未ログイン
* ログイン処理中
* セッション確立済み
* タブ作成済み
* テナントアクセス準備中
* テナントアクセス可能
* 業務API実行中
* タブ終了処理中
* セッション終了処理中
* エラー・復旧処理中

実際のシステムに存在しない状態を、既存仕様として追加しないでください。分析上必要な抽象状態を追加する場合は、分析用のモデルであると明記してください。

各遷移について、遷移条件、実行API、変更される状態、失敗時の状態を整理してください。

## タスク3：複数テナントの同時操作

1つのセッション内に複数のタブIDが存在し、それぞれが別のテナントを操作する場合について分析してください。

特に以下を確認してください。

* タブ単位で独立している状態
* セッション全体で共有される状態
* テナントアクセス用tokenの対応関係
* 一方のタブの操作が他方に影響する可能性
* 同一セッション内での並行リクエストの可否
* 共有セッションを再生成した場合の影響

## タスク4：ライフサイクル

以下を整理してください。

* セッション開始から終了まで
* タブ作成から終了まで
* テナントアクセス開始から終了まで
* セッション失効時の影響範囲
* Redisデータの期限切れ・欠落時の挙動
* 途中で失敗した処理の後始末

## 出力形式

1. API依存関係図
2. 状態遷移図
3. 各状態の定義
4. 遷移条件と副作用の一覧
5. 並行操作に関する分析
6. 失敗時の残存状態
7. 未確定事項と追加調査項目

図はMermaid形式でも提示してください。

ソースコードから確認できた事実と、設計上の抽象化・推測を明確に区別してください。

## プロンプト2-B：状態遷移のレビュー

LLMが作成した状態遷移図を、そのまま採用せず、矛盾がないか検証します。

以下の既存システム分析レポート、状態遷移図、API依存関係図をレビューしてください。

## レビュー観点

1. 状態遷移図に、ソースコード上の根拠がない遷移が含まれていないか。
2. APIの呼び出し順序が既存実装と一致しているか。
3. 状態を変更するAPIが漏れていないか。

5. タブの終了とセッションの終了が混同されていないか。
6. セッション失効時に、複数タブの状態がどうなるか明確か。

9. リトライによって同じタブやテナントアクセス状態が重複作成されないか。
10. 未確定の仕様が、確定事項として記載されていないか。

## 出力

各指摘について、次を示してください。

* 重大度：Critical / High / Medium / Low
* 問題点
* 根拠
* 発生条件
* 影響

* 追加確認の必要性

# 工程3：新API層の設計

## 目的

ここから初めて、新APIの設計を行います。

設計の中心は、**呼び出し元から見た操作コンテキストと、既存システム内部の状態を対応付けること**です。

呼び出し元に公開するAPIと、内部で使用するAPIを明確に分けます。

## インプット

* 工程1の既存システム分析レポート
* 工程2の状態遷移図
* 既存API一覧
* 呼び出し元が実現したい業務操作の要件
* 新API層の実行環境や使用言語など、既に決まっている技術条件

この段階で、未確定の要件は質問として残します。

## プロンプト3-A：新APIの仕様設計

あなたは、既存システムに新しいBFF / Adapter API層を追加するシステムアーキテクトです。

工程1の既存システム分析レポートと、工程2の状態遷移図・API依存関係図をもとに、新API層の設計を行ってください。

この段階では設計書のみを作成し、実装コードは生成しないでください。

## 目的

既存システムの複雑なAPIを隠蔽し、呼び出し元が簡単なAPIで業務操作できるようにします。

呼び出し元に、既存システムのユーザーID、セッションID、タブID、テナントアクセス用tokenを直接扱わせません。

呼び出し元は、必要に応じてテナントを指定します。

既存システムにはAPI専用ユーザーでアクセスし、既存システムのセッションとタブを内部で管理します。

複数テナントの同時操作は、既存システムのタブIDによって状態を分離する仕組みを利用します。

## 設計方針

* 呼び出し元に不要な内部情報を公開しない。
* 新API用tokenと既存システムの内部tokenを区別する。
* 既存システムのAPI呼び出し順序を守る。
* テナント操作状態をタブ単位で分離する。
* 既存システムの仕様を推測で変更しない。
* Redisに保存する状態は必要最小限にする。
* 既存システムの状態と新API用Redisの状態の整合性を考慮する。
* 認証・認可の責務を明確にする。
* 未確定事項を勝手に確定しない。

* リトライで二重実行されないか。
* Redis障害時の動作が適切か。

### 5. セキュリティ

* tokenや秘密情報がログに出ていないか。
* API専用ユーザーの権限が必要最小限か。
* テナントアクセス権が適切に確認されるか。
* 外部入力が適切に検証されるか。
* エラー応答から内部情報が漏えいしないか。

### 6. テスト

* 重要な正常系・異常系が網羅されているか。
* 複数テナントの同時操作がテストされているか。
* テストが実装の内部構造に過度に依存していないか。
* 実際にテストが実行されたか。

## 出力

問題ごとに以下を示してください。

* 重大度
* 対象ファイルと箇所
* 問題の内容
* 発生条件
* 影響
* 修正案
* 必要なテスト

最後に、設計適合性、テスト状況、残存リスクを総括してください。

問題を検出しただけで、テスト未実行の実装を安全と断定しないでください。

# 7. すべての工程で使う共通ルール

ここまでの各プロンプトに加え、プロジェクト共通の指示を用意しておくと、工程間のブレを減らせます。

例えば、リポジトリのルートに `LLM_DEVELOPMENT_RULES.md` として保存し、各工程で参照させます。

# LLM開発共通ルール

## 1. 基本方針

このプロジェクトでは、既存システムのソースコードを分析し、仕様・設計・実装・テストの順に段階的に開発する。

各工程の成果物は、次工程の入力として利用する。

## 2. 事実と推測の区別

以下を明確に区別する。

* ソースコードから確認できた事実
* テストから確認できた事実
* 設計上の提案
* 推測
* 未確定事項

根拠がない事項を確定仕様として扱わない。

## 3. 根拠の提示

既存システムに関する説明では、可能な限り以下を示す。

* ファイルパス
* クラス・関数名
* 関連するAPI
* 関連するテスト

実際に確認していないファイルの内容を推測で説明しない。

## 4. 状態管理

次の概念を混同しない。

* API専用ユーザー
* API用token
* 既存システムのセッション
* タブID
* テナントID
* テナントアクセス用token
* 新API層の操作コンテキスト

各概念の責務とライフサイクルを明確にする。

## 5. テナント分離

同一セッション内で複数テナントを同時操作できることを重要な要件とする。

タブIDによる既存システムの状態分離を利用し、テナント間の状態混在を防ぐ。

ただし、既存システムがセッション単位で共有する状態については、ソースコードから確認し、必要な競合対策を設計する。

## 6. セキュリティ

* tokenと秘密情報をログに出力しない。
* 内部tokenを不要に公開しない。
* API用tokenを認証情報として適切に保護する。
* テナント指定だけでアクセス権が保証されると考えない。
* API専用ユーザーの権限を必要最小限にする。
* Redisへのアクセス権限と保存情報を適切に管理する。

## 7. 実装方針

* 承認済み設計に基づいて実装する。
* 対象タスク以外の変更を最小限にする。
* エラー処理とテストを省略しない。
* 既存プロジェクトの規約を優先する。
* 設計上の矛盾を発見した場合は、勝手に回避せず指摘する。

## 8. テストと報告

テストの実行結果を正確に報告する。

未実行のテストを成功と報告しない。

不明点、残存リスク、未実装項目を明示する。

# 8. 工程間で成果物をどう受け渡すか

ここは実際の開発で重要です。

毎回、過去の会話履歴をすべてLLMに読ませるのではなく、**成果物をファイルとして保存し、次工程で明示的に渡す**方法をおすすめします。

例えば、次のような構成です。

```text
project/
  docs/
    00-requirements.md

    01-analysis/
      repository-map.md
      existing-api-inventory.md
      session-tab-tenant-analysis.md
      redis-analysis.md

    02-state-model/
      state-transitions.md
      api-dependencies.md
      review-results.md

    03-design/
      architecture.md
      api-spec.yaml
      redis-design.md
      data-model.md

    04-reliability-security/
      error-handling.md
      concurrency.md
      security.md

    05-implementation/
      implementation-plan.md

  src/
  tests/
```

これは推奨例です。既存プロジェクトにドキュメント規約がある場合は、そちらに合わせてください。

### ファイルの受け渡しルール

各工程で、以下を実施します。

1. 成果物をファイルとして保存する。
2. レビュー結果を反映する。
3. 変更した内容と未確定事項を記録する。
4. 次工程では、必要な成果物と関連ソースコードを明示的に入力する。
5. 仕様が変わった場合は、影響する設計・テストも更新する。

特に、Redisのデータ構造やセッション管理の仕様が変更された場合は、実装だけを直すのではなく、設計書とテストも更新します。

# 9. LLMへの入力を効率化する方法

今回のように既存システムが大規模な場合、すべてのソースコードを毎回入力する必要はありません。

工程ごとに必要な範囲を絞ります。

| 工程 | 主に入力するもの                       |
| -- | ------------------------------ |
| 1  | リポジトリ構成、認証・セッション・タブ・Redis関連コード |
| 2  | 工程1の分析結果、状態変更に関係するソースコード、関連テスト |
| 3  | 工程1・2の成果物、業務要件、既存API一覧         |
| 4  | 工程1〜3の成果物、関連する実装               |
| 5  | 承認済み設計、プロジェクト構成、既存規約           |
| 6  | 対象タスク、関連設計、変更対象コード、関連テスト       |

ただし、分析結果の根拠を再確認する場合は、元のソースコードも再度参照させます。**前工程のLLMが書いたレポートだけを真実として扱わない**ことが大切です。

また、各工程の入力が大きすぎる場合は、モジュール単位で分析し、最後に統合させます。

# 10. 最も重要な追加ポイント：工程1の結果をどう検証するか

このプロジェクトでは、特に次の3点を早い段階で確認することをおすすめします。

### ① タブIDによる分離がどこまで有効か

タブIDごとにテナントの操作状態が分離されているとしても、セッション単位の共有状態が残っている可能性があります。

例えば、テナントアクセス時に共有セッションの値が変更される実装であれば、タブIDだけでは競合を防げない可能性があります。

そのため、工程1で「タブIDが引き継がれるか」を確認するだけでは不十分です。**タブIDを使わずに共有セッションの状態を変更する処理が存在しないか**まで確認します。

### ② API専用ユーザーのセッションをどの範囲で共有するか

API専用ユーザーを1つ用意する場合でも、内部セッションを常に1つだけ共有するかどうかは別の設計判断です。

共有範囲によって、障害時の影響、同時実行、セッション失効時の復旧、アクセス範囲の管理が変わります。

工程3で複数の選択肢を比較し、既存システムの制約と運用要件を踏まえて決定してください。

### ③ 新API用tokenの役割を明確にする

新API用tokenが何を識別するのかを明確にします。

例えば、次のような違いがあります。

* セッション全体を識別するtoken
* テナント操作コンテキストを識別するtoken
* 1つの業務処理だけに使う短命のtoken

今回の要件ではテナント操作コンテキスト単位の識別が有力な候補ですが、呼び出し元の利用形態やセッション共有範囲を確認してから確定するのがよいでしょう。

# 11. 私なら、最初の1週間はこう進めます

実際の進め方としては、以下をおすすめします。

**1日目：既存システムの構造調査**

リポジトリ構成、API一覧、認証・セッション関連コードを分析します。

**2日目：タブとテナントアクセスの解析**

タブID、テナントアクセス用token、Redisの関係を調査します。

**3日目：状態遷移図と依存関係図の作成・レビュー**

既存APIの呼び出し順序と状態変更を整理し、ソースコードと照合します。

**4日目：新APIとRedisの設計**

公開API、操作コンテキスト、内部状態の対応関係を設計します。

**5日目：異常系・競合・実装計画のレビュー**

セッション失効、途中失敗、並行操作などの仕様を確認し、実装タスクを確定します。

これは目安であり、リポジトリの規模や調査結果によって調整してください。大規模なシステムであれば、解析とレビューにもっと時間をかける価値があります。

---

## 最後に：この進め方で最も大切なこと

今回のようなシステムでは、LLMにコードを生成させる能力そのものより、**既存システムの状態管理を正しく理解させ、その理解を検証可能な設計書として残すこと**の方が重要です。

特に、セッションID・タブID・テナントアクセス用token・2種類のRedisの関係を正確に把握できれば、その後の設計と実装は進めやすくなります。

おすすめの進め方は、次のとおりです。

1. 工程1-Aでリポジトリ構成を分析する。
2. 工程1-Bでセッション・タブ・テナントアクセスを分析する。
3. 分析結果を元のソースコードと照合する。
4. 工程2で状態遷移とAPI依存関係を確定する。
5. 工程3以降で新API層を設計し、実装する。

**まずは工程1から始め、既存システムの実際の動作を確定させることをおすすめします。** その分析結果を基にすれば、後続工程の設計精度を大きく高められます。
