既存のソースコード（リポジトリ）だけをインプットにして、AI（コードエージェント）にテスト仕様書（大中小の項目）をMarkdown形式で出力させるためのプロンプトですね。

AIに指示を出す際の最大のコツは、**「コードのどこに注目して大中小を切り分ければいいか」の明確な基準（マッピングルール）をあらかじめ提示しておくこと**です。これがブレると、AIは適当に項目を作ってしまいます。

以下に、フロントエンド、バックエンド、クライアント（モバイル/デスクトップアプリ）それぞれの特性に合わせた、そのままコピー＆ペーストして使える指示用Markdownプロンプトを提示します。

---

## 1. フロントエンド（React, Vue, Next.jsなど）向けプロンプト

フロントエンドは「コンポーネントの階層」「画面遷移（ルーター）」「ユーザーの操作（イベント）」に主眼を置きます。

```markdown
# 依頼：フロントエンドのテスト仕様書（テスト項目）の生成

仕様書がない既存のソースコード（フロントエンド）を解析し、単体テスト、結合テスト、システムテストの各テスト工程における「大項目・中項目・小項目」のリストをMarkdownのテーブル形式で出力してください。

## 1. 分類ルール（マッピング基準）
各テスト工程における大中小項目は、以下の基準でコードから抽出・分類してください。

### 【単体テスト】
* **大項目:** コンポーネント名（またはHooks名、Utilityファイル名）
* **中項目:** 関数名、メソッド名、またはUI要素（ボタン、フォームなど）の初期状態
* **小項目:** propsの条件、状態（State）の変化、ユーザー操作（Click等）による発火条件、期待される表示・挙動

### 【結合テスト】
* **大項目:** 画面（Page）単位、または主要な機能ブロック（例：ダッシュボード、設定ウィザード）
* **中項目:** 画面間の遷移、コンポーネント間のデータ受け渡し（Context/Redux等）、API通信（Hooks経由のデータ取得）
* **小項目:** 正常なデータ取得時の表示、APIエラー時のフォールバック表示、ローディング状態の挙動

### 【システムテスト】
* **大項目:** ユーザーの目的（ユースケース / 画面全体の役割）
* **中項目:** 業務シナリオ（例：ログイン → 商品検索 → カート追加 → 決済遷移）
* **小項目:** 特定ブラウザ/デバイス環境、ユーザー権限（一般/管理者）ごとの挙動、レスポンシブ表示（PC/SP）

## 2. 出力フォーマット
各テスト工程ごとに、以下のテーブル形式で出力してください。

### [テスト工程名（例：単体テスト）]
| 大項目 | 中項目 | 小項目（テスト条件と期待される結果） |
| :--- | :--- | :--- |
| | | |

```

## 2. バックエンド（Web API, マイクロサービスなど）向けプロンプト

バックエンドは「エンドポイント（ルーティング）」「ビジネスロジック（サービス層）」「データベースや外部APIとの連携」に主眼を置きます。

```markdown
# 依頼：バックエンドのテスト仕様書（テスト項目）の生成

仕様書がない既存のソースコード（バックエンド）を解析し、単体テスト、結合テスト、システムテストの各テスト工程における「大項目・中項目・小項目」のリストをMarkdownのテーブル形式で出力してください。

## 1. 分類ルール（マッピング基準）
各テスト工程における大中小項目は、以下の基準でコードから抽出・分類してください。

### 【単体テスト】
* **大項目:** クラス名、モジュール名（Service層、バリデーションロジック、共通ロジック等）
* **中項目:** 関数名、メソッド名
* **小項目:** 引数の境界値、正常系/異常系の条件（例外スロー）、返り値の検証（モックを前提としたロジック単体の検証）

### 【結合テスト】
* **大項目:** コントローラー（Controller/Resolver）またはエンドポイントのグループ（例：`/api/v1/users`）
* **中項目:** 各HTTPメソッド（GET/POST/PUT/DELETE）と、DB（Repository層）や外部APIとの連携処理
* **小項目:** ステータスコード（200, 400, 401, 500等）、レスポンスJSONの構造、DBへのレコード永続化の成否、トランザクションのロールバック検証

### 【システムテスト】
* **大項目:** 主要なAPI機能（例：認証・認可機能、注文決済パイプライン）
* **中項目:** 業務シナリオ（例：ユーザー作成 → ログイン → トークンを用いたデータ取得の一連の流れ）
* **小項目:** パフォーマンス（応答時間）、大量データ処理、認証トークン切れ（Exp）時の挙動、セキュリティ（SQLインジェクションや不正アクセス対策）
```

## 3. クライアント（iOS/Android、Flutter、Desktopアプリなど）向けプロンプト

クライアントアプリは、フロントエンドに似ていますが「ライフサイクル（起動・バックグラウンド）」「端末固有の機能（カメラ、位置情報、通知）」「オフライン対応（ローカルDB）」を考慮する必要があります。

```markdown
# 依頼：クライアントアプリのテスト仕様書（テスト項目）の生成

仕様書がない既存のソースコード（モバイル/デスクトップアプリ）を解析し、単体テスト、結合テスト、システムテストの各テスト工程における「大項目・中項目・小項目」のリストをMarkdownのテーブル形式で出力してください。

## 1. 分類ルール（マッピング基準）
各テスト工程における大中小項目は、以下の基準でコードから抽出・分類してください。

### 【単体テスト】
* **大項目:** ViewModel名、Presenter名、またはビジネスロジックを持つクラス・構造体
* **中項目:** メソッド名、プロパティの変更ロジック
* **小項目:** 入力値に対する状態（State）の変化、イベント発火時のストリーム（Rx/Coroutines/Combine等）の出力検証

### 【結合テスト】
* **大項目:** 画面（ViewController / Activity / Fragment / Screen）
* **中項目:** 画面遷移、ローカルDB（SQLite/Realm等）とのデータ同期、ネットワーク通信レイヤーとの連携
* **小項目:** 通信エラー（機内モード等）のダイアログ表示、バックグラウンドから復帰（レジューム）時の挙動、プッシュ通知タップからのディープリンク遷移

### 【システムテスト】
* **大項目:** アプリ全体の主要なユーザー体験（ユースケース）
* **中項目:** 端末の状態変化を伴う業務シナリオ（例：ログイン後、カメラでQRコードを読み取り、データをサーバーに送信する）
* **小項目:** OSバージョン違い、端末の権限設定（カメラ許可/拒否）、ダークモード切り替え、メモリ負荷時の挙動
```

## 💡 エージェントを上手く動かすための補足アドバイス

* **コードベースが巨大な場合：** 全コードを一度に渡すとAIの文脈制限（コンテキストウィンドウ）を超えたり、精度が落ちたりします。「今回は〇〇モジュールのコードをインプットにするので、これに対するテスト項目を作って」と**対象を絞って段階的に実行**するのがベストです。
* **出力後の調整：** 最初から完璧なケースは出ないことが多いので、「この結合テストの小項目に、データが空（Empty）だった場合のパターンを追加して」などと、チャットで徐々に肉付けしていくと実用的なテスト仕様書に仕上がります。
