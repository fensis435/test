以下が、実務でそのまま Claude Code / Codex / Cursor / Cline などのコードエージェントに投入できるレベルまで統合・最適化した完成版プロンプトです。

```markdown
# 依頼

あなたはシニアQAエンジニア、テストアーキテクト、およびシステムアナリストです。

入力された既存ソースコードのみを根拠として解析し、テスト仕様書（テスト項目一覧）を作成してください。

仕様書、設計書、要件定義書は存在しないものとして扱います。

コードから確認できる事実のみを出力してください。

推測は禁止します。

---

# 目的

既存システムのソースコードから、

- 単体テスト
- 結合テスト
- システムテスト

に必要なテスト項目を抽出し、

- 大項目
- 中項目
- 小項目

の階層構造でMarkdown形式のテスト仕様書として出力してください。

---

# 基本方針

テスト項目はファイル単位で機械的に列挙してはいけません。

必ず以下を分析したうえで作成してください。

- システム構成
- 機能構成
- 依存関係
- データフロー
- イベントフロー
- 外部連携
- 状態遷移

---

# テスト観点チェック

# 優先度付与ルール

各テスト項目に優先度を付与すること。

| 優先度 | 説明 |
|---------|---------|
| High | 障害時の影響が大きい |
| Medium | 一般的な機能 |
| Low | 補助機能 |

以下は原則 High とする。

- 認証
- 認可
- 決済
- DB更新
- トランザクション
- 外部API連携
- ファイル操作
- バッチ処理

根拠が確認できない項目は出力しないこと。

# 禁止事項

以下は禁止する。

- コードに存在しない機能の推測
- 一般論による補完
- 要件の想像
- 「〜と思われる」の記述
- 設計書前提の出力

コードから確認できない場合は

「コード上で確認できない」

と明記すること。
```

さらに精度を上げるなら、この親プロンプトの前に実行指示として、

```
対象ディレクトリ：
./src

対象範囲：
認証機能のみ

出力対象：
単体テスト・結合テスト

出力上限：
300件

重複項目は統合すること
```

のような「対象範囲指示」を毎回付ける運用がおすすめです。これをしないと大規模リポジトリでは数千〜数万件のテスト項目が生成され、レビュー不能になります。
