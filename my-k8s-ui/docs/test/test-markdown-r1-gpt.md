添付内容を評価すると、現在のプロンプトは「大中小項目の分類ルール」は明確ですが、実務でAIエージェントにテスト仕様書を生成させるには以下の弱点があります。

### 現状の課題

1. **出力品質の判定基準がない**

   * AIが推測で項目を作る余地がある
   * コードから根拠を抽出するルールがない

2. **網羅性の指示が弱い**

   * 正常系中心になりやすい
   * 異常系、境界値、権限制御、例外処理が漏れやすい

3. **コード解析の優先順位がない**

   * Controller → Service → Repository
   * Page → Component → Hook
     といった解析順序が指定されていない

4. **出力粒度が不安定**

   * AIによって大項目数が変わる
   * 小項目の粒度がバラつく

5. **テスト観点が不足**

   * 境界値
   * 例外
   * 権限
   * 排他
   * 性能
   * セキュリティ

が明示されていない

---

# 推奨版（汎用・最適化版）

実際のコードエージェントに渡すなら、フロントエンド／バックエンド別ではなく、まず以下の共通プロンプトを親プロンプトとして使う方が精度が上がります。

```markdown
# 依頼

あなたはシニアQAエンジニア兼システムアナリストです。

入力された既存ソースコードのみを根拠として解析を行い、
テスト仕様書のドラフトを作成してください。

仕様書や設計書が存在しない前提とします。

推測は禁止です。

コードから確認できる内容のみを出力してください。

---

# 目的

テスト工程ごとに

- 大項目
- 中項目
- 小項目

を抽出し、
Markdown形式のテスト仕様書として出力してください。

- 設計書前提の記述

「コード上で確認できない」
```

### この改良版の利点

* AIの推測を抑制できる
* コードベースからの根拠追跡ができる
* 「根拠コード」列を持たせるためレビューしやすい
* テスト観点の漏れが大幅に減る
* Claude Code、Codex、Gemini CLI、Cursor Agent、Cline などのコードエージェントで安定して動作する

特に実案件でテスト仕様書を起こすなら、「根拠コード列」と「推測禁止」を入れるだけで出力品質がかなり向上します。
