はい。今の構成なら、**かなり素直に試験環境を組めます**。

ただし、まず一つ重要な設計点があります。

> **SSMのCLIをUbuntu Server上で実行するなら、dnsmasqのAWS向け名前解決は `127.0.0.1` ではなく、Ubuntu Server自身のイントラ側IPへ向ける**

のがよいです。

そうすると、

```text
Chrome (Windows VM)
   │
   │ DNS: foo.dev.local
   ▼
Ubuntu Server
   │
   │ foo.dev.local → UbuntuのイントラIP
   ▼
Ubuntu:8443
   │
   │ SSM port forwarding
   ▼
Bastion EC2
   │
   │ TCP/443
   ▼
Internal ALB
   │
   ▼
NGINX Ingress
   │
   ▼
Envoy
   │
   ▼
GUI / Tentnas
```

という構成になります。

以下、**「まず動かす」ことを目的にした最小構成**として具体化します。

*.dev.example.internal

# 1. dnsmasq

## 1-1. 一番簡単な設定

Ubuntuのdnsmasqに、

```text
*.dev.example.internal
```

をUbuntu自身へ向ける設定を入れます。

例えば：

```text
/etc/dnsmasq.d/aws-dev.conf
```

```ini
address=/dev.example.internal/192.168.10.10
```

dnsmasqの`address`設定は、指定したドメイン配下の名前に対して指定IPを返すため、今回のワイルドカード用途に使えます。該当ドメインの問い合わせは上流DNSへ転送されず、このアドレスで応答されます。([Linux Die][1])

例えば：

```text
foo.dev.example.internal
bar.dev.example.internal
gui.dev.example.internal
```

全部、

```text
192.168.10.10
```

になります。

### 重要

ここで

```ini
address=/dev.example.internal/127.0.0.1
```

としてはいけません。

Chromeから見る`127.0.0.1`は**Windows VM自身**だからです。

今回SSMをUbuntuで動かすので、

```text
Windows
   ↓
192.168.10.10:8443
   ↓
Ubuntu
```

とします。

# 2. dnsmasqの既存設定との共存

今、

> 登録がない場合はイントラDNSへ流す

という構成ができているとのことなので、基本的には既存設定を壊さず、

```ini
address=/dev.example.internal/192.168.10.10
```

を追加するだけでよいです。

例えば：

```ini
# /etc/dnsmasq.d/aws-dev.conf

# AWS/EKS開発環境
address=/dev.example.internal/192.168.10.10
```

その後：

```bash
sudo systemctl restart dnsmasq
```

確認：

```bash
dig @192.168.10.10 foo.dev.example.internal
```

期待値：

```text
foo.dev.example.internal.  0 IN A 192.168.10.10
```

Windowsからも、

```powershell
nslookup foo.dev.example.internal 192.168.10.10
```

として、

```text
Name:    foo.dev.example.internal
Address: 192.168.10.10
```

になればOKです。

ここは重要です。

AWS CLIから

```bash

```

を実行する場合、**Ubuntu側にSession Manager Pluginが必要**です。AWS公式にも、CLIでSession Managerを使う場合はCLIだけでなくSession Manager Pluginが必要とされています。([AWS ドキュメント][2])

確認：

```bash
session-manager-plugin
```

成功すれば、

```text
The Session Manager plugin is installed successfully.
```

のような表示になります。([AWS ドキュメント][3])

# 4. SSMで「EC2 → ALB」をポートフォワード

今回のキモです。

通常の

```text
AWS-StartPortForwardingSession
```

ではなく、

```text
AWS-StartPortForwardingSessionToRemoteHost
```

を使います。

AWS公式にも、このドキュメントで

```text
local machine
   ↓
managed EC2
   ↓
remote host
```

へのTCPポートフォワードが可能と記載されています。

さらに重要なのは、**remote hostはSSM管理対象でなくてもよい**ことです。([AWS ドキュメント][4])

つまり、

```text
Ubuntu
   ↓ SSM
Bastion EC2
   ↓
Internal ALB
```

が可能です。

# 5. ALBのDNS名を調べる

UbuntuからAWS CLIで：

```bash
aws elbv2 describe-load-balancers \
  --names my-internal-alb \
  --query 'LoadBalancers[0].[DNSName,Scheme,State.Code]' \
  --output table
```

例えば：

```text
-------------------------------------------------
|              DescribeLoadBalancers             |
+------------------+-----------+----------------+
| internal-xxx.... | internal  | active         |
+------------------+-----------+----------------+
```

ここで`Scheme`が

```text
internal
```

ならInternal ALBです。

AWSのALBは`internal`と`internet-facing`の2種類で、Internalの場合はプライベートIPだけを持ち、VPCへ到達できるクライアントからのみ利用できます。([AWS ドキュメント][5])

# 6. Bastion EC2からALBへ到達できることを確認

これは**SSMを試す前に絶対確認した方がいい**です。

まず：

```bash
aws ssm start-session --target i-xxxxxxxx
```

でBastionへ入ります。

そしてBastion上で：

```bash
curl -vk https://internal-xxxxxxxx.ap-northeast-1.elb.amazonaws.com/
```

これがALBまで到達することを確認します。

もしTLSのHost/SNIまで確認したいなら、ALBの実際のホスト名ではなく、試験ドメインを指定して：

```bash
curl -vk \
  --resolve foo.dev.example.internal:443:10.0.2.100 \
  https://foo.dev.example.internal/
```

のようなテストもできます。

ただしALBのIPを固定するのは本番構成ではありません。単純に「Bastion → ALBが通るか」を確認するなら、ALBのDNS名で十分です。

# 7. ALBのSecurity Group

ここはかなり重要です。

ALBのSGに、

```text
TCP 443
Source: Bastion EC2のSecurity Group
```

を許可します。

例えば：

```text
ALB-SG inbound

HTTPS 443
Source:
sg-bastion
```

という形。

CIDRで

```text
10.0.1.0/24
```

でも動きますが、可能ならSG参照にした方が綺麗です。

つまり：

```text
Bastion EC2
  SG: sg-bastion
       │
       │ 443
       ▼
ALB
  SG: sg-alb
       │
       └── inbound:
           443 from sg-bastion
```

です。

# 8. SSM RemoteHost Port Forward

Ubuntuで：

```bash
aws ssm start-session \
  --target i-xxxxxxxxxxxxxxxxx \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{
    "host":["internal-xxxxxxxx.ap-northeast-1.elb.amazonaws.com"],
    "portNumber":["443"],
    "localPortNumber":["8443"]
  }'
```

AWS公式の形式もこの`AWS-StartPortForwardingSessionToRemoteHost`＋`host`＋`portNumber`＋`localPortNumber`という構成です。RemoteHostへの名前解決・ネットワーク到達性はManaged Node側で成立している必要があります。([AWS ドキュメント][4])

つまり実際の通信は：

```text
Ubuntu
192.168.10.10:8443
       │
       │ SSM
       ▼
Bastion EC2
       │
       │ TCP 443
       ▼
Internal ALB
```

です。

# 10. Hostヘッダはどうなる？

ここが今回の実験の重要ポイントです。

Chromeが送るのは概念的には：

```http
GET / HTTP/1.1
Host: foo.dev.example.internal:8443
```

HTTPSなのでTLSのSNIにも：

```text
foo.dev.example.internal
```

が入ります。

SSMはHTTPプロキシではないので、**HTTP Hostを書き換えません**。

したがってALB/NGINX側には、基本的に

```text
foo.dev.example.internal
```

という元のホスト名が届きます。

これによって、

```text
foo.dev.example.internal
        ↓
NGINX Ingress
        ↓
foo service
```

というHostベースルーティングを試せます。

# 11. NGINX Ingress側

もし既にNGINX Ingressがあるなら、例えば：

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: test
  namespace: test
spec:
  ingressClassName: nginx
  rules:
    - host: foo.dev.example.internal
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: foo
                port:
                  number: 80
```

でOKです。

ワイルドカードを試すなら：

```yaml
spec:
  rules:
    - host: "*.dev.example.internal"
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: foo
                port:
                  number: 80
```

Kubernetes IngressのワイルドカードHostについては、サブドメイン部分に対するマッチングという制約があります。

# 15. ただし `:8443` がHostヘッダに入る点

今回の構成で一つだけ注意したいのがこれです。

ブラウザURLが：

```text
https://foo.dev.example.internal:8443
```

なのでHTTP/1.1ではHostが：

```text
Host: foo.dev.example.internal:8443
```

になる可能性があります。

通常のIngressのHostマッチングではポート番号を除いて扱うため問題にならないケースが多いですが、**厳密にオンプレと同じリクエストにしたいなら、443で受ける**方が綺麗です。

つまりUbuntu側を：

```text
192.168.10.10:443
```

で待ち受けさせ、

```text
https://foo.dev.example.internal/
```

にします。

ただしLinuxの1024未満のポートを一般ユーザーでbindする問題があります。

試験ならまず：

```text
https://foo.dev.example.internal:8443
```

で動作確認してしまうのがおすすめです。

# 16. SSM側のIAM

ユーザーのIAMには最低限、Session Managerのセッション開始に必要な権限が必要です。

また、`AWS-StartPortForwardingSessionToRemoteHost`というドキュメントを指定するので、IAMポリシーでそのDocumentへの利用が制限されている場合は許可が必要です。AWS公式にも、デフォルトSession Document以外を指定する場合はそのDocumentへの権限が必要とされています。([AWS ドキュメント][6])

ざっくり試験用なら、

```json
{
  "Effect": "Allow",
  "Action": [
    "ssm:StartSession"
  ],
  "Resource": [
    "arn:aws:ec2:ap-northeast-1:123456789012:instance/i-xxxxxxxx"
  ]
}
```

に加えてDocumentへの権限が必要になる構成があります。

実際の企業IAMポリシーに合わせる必要があります。

確認：

```bash

```

または環境によって：

```bash
systemctl status amazon-ssm-agent
```

です。

# 18. VPC Endpoint

現在、

```text
VPCE用サブネット
```

があるとのことなので、おそらく既に：

```text
com.amazonaws.ap-northeast-1.ssm
com.amazonaws.ap-northeast-1.ssmmessages
com.amazonaws.ap-northeast-1.ec2messages
```

あたりを作っているのだと思います。

Private EC2でSSMを利用する場合、AWSは`ssm`、`ssmmessages`、`ec2messages`へのHTTPS/443到達性を要求しています。VPC Interface Endpointを使えばインターネット/NATなしでSystems Managerを利用できます。([AWS ドキュメント][7])

特に最近のSSM Agentでは`ssmmessages`が重要です。AWSのドキュメントではAgent 3.3.40.0以降、利用可能なら`ssmmessages`を優先するようになっています。([AWS ドキュメント][8])

なので、

```text
Bastion EC2
   │
   ├── VPCE → SSM
   ├── VPCE → SSMMessages
   └── VPCE → EC2Messages（必要な環境の場合）
```

が通っていればOKです。

# 22. ここで一つだけ、今の構成で確認したいこと

**「ALB → NGINX Ingress」部分がどう実装されているか**だけ確認したいです。

例えば、

### A

```text
Internal ALB
  ↓
NGINX Service
(type: NodePort)
```

なのか、

### B

```text
Internal ALB
  ↓
AWS Load Balancer Controller
  ↓
NGINX
```

なのか、

### C

```text
Internal ALB
  ↓
Target Group
  ↓
NGINX PodのIP
```

なのかで、**ALBのSecurity Group / Target Group / Listener設定の確認ポイントが変わります**。

もし現在のALBがすでに正常に

```text
ALB → NGINX → Envoy → GUI/Tentnas
```

まで通っているのであれば、今回の試験のためにALB自体を作り直したり、Ingressを変更したりする必要は基本ありません。

**まずは既存ALBをそのまま使い、`dnsmasq → Ubuntu:8443 → SSM RemoteHost → Internal ALB:443` を追加するだけ**、というのが一番安全です。
