なるほど、これでかなり明確になりました。
この構成なら、**オンプレでやっていた「ローカルDNS → ワイルドカード → Ingress」の考え方を、かなりそのままAWS側で試せます。**

まず、私の理解を図にするとこうです。

```text
【イントラ / ローカル環境】

┌──────────────────────────────┐
│ 踏み台 Windows VM            │

               │
               │ イントラ
               ▼
┌──────────────────────────────┐

               │
               │ SSM

│                              │

│                              │
```

そして今回試したいのは、

```text
Chrome
  ↓

  ↓

  ↓
NGINX Ingress
  ↓

  ↓
GUI / Tentnas
```

という経路ですね。

## この構成なら「ローカルDNS」をそのまま活かせます

むしろ、**Chromeの `--host-rules` は今回の構成では不要になる可能性が高い**です。

例えばローカルDNSに、

```text
*.dev.example.internal
```

を登録して、

```text
app.dev.example.internal
tentnas.dev.example.internal
foo.dev.example.internal
```

などをAWS側のALBへ向けます。

ただし、ここで一つ重要なのは、

> **ALBが Internet-facing ALB なのか Internal ALB なのか**

です。

お話からすると、

> 最終的にインターネットへ接続するため、かつWAFを使いたい

とのことなので、おそらく **Internet-facing ALB** ですよね。

そうであれば、構成としてはむしろ、

```text
Chrome
  │
  │ app.dev.example.internal
  ▼
ローカルDNS
  │
  │ ALBのDNS名
  ▼
SSM
  │
  ▼
EC2
  │
  ▼
Internet-facing ALB
  │
  ▼
NGINX Ingress
  │
  ▼
Envoy
  │
  ▼
GUI / Tentnas
```

という形を試せます。

---

## そして、ここで「Hostヘッダ」が効いてきます

例えばChromeで、

```text
https://foo.dev.example.internal/
```

と入力します。

DNSは、

```text
foo.dev.example.internal
        ↓
ALB
```

と解決するだけです。

HTTP的には、

```http
GET /
Host: foo.dev.example.internal
```

となります。

HTTPSならさらにTLSのSNIにも、

```text
foo.dev.example.internal
```

が入ります。

そのままSSMがTCPレベルで転送すれば、

```text
Chrome
  │
  │ TLS
  │ SNI: foo.dev.example.internal
  │ Host: foo.dev.example.internal
  ▼
SSM
  ▼
ALB
```

となるので、**ALB/Ingress側で元のホスト名を使ったルーティングが可能**です。

# ここで一つ大事な修正

先ほどまで私は、

```text
Chrome
 ↓
SSM
 ↓
Internal ALB/NLB
```

という方向で話していましたが、**今回の実際の構成を聞く限り、そこを無理にInternal LBにする必要はありません。**

むしろ、

```text
Internet-facing ALB
        ↓
NGINX Ingress
        ↓
Envoy
```

という、**本番に近い構成そのものをSSM経由で試す**のが今回の目的に合っています。

WAFも含めて確認したいなら、なおさらです。

---

## ただし、SSMでALBに到達させる部分は確認が必要

SSMの

```text
AWS-StartPortForwardingSessionToRemoteHost
```

を使えば、

```text
Windows / Ubuntu
      │
      │ localhost:8443
      ▼
     SSM
      │
      ▼
EC2
      │
      │ TCP 443
      ▼
ALB
```

という形にできます。

ここで重要なのは、**SSMはHTTPプロキシではなくTCP転送**だということです。

だから、

```text
Host: foo.dev.example.internal
SNI: foo.dev.example.internal
```

をSSMが書き換えるわけではありません。

そのままALBまで届きます。

これは今回かなり都合がいいです。

---

# ただ、DNSの向きは少し考える必要があります

ここが今回の実験で一番面白いところです。

ローカルDNSで、

```text
foo.dev.example.internal
       ↓
ALB
```

としたい。

一方、Chromeが直接ALBへ接続すると、

```text
Chrome → ALB
```

になってしまいます。

**SSMを経由したいなら、Chromeから見える名前解決と、SSMの接続先を分離する必要があります。**

例えば：

```text
Chrome
  │
  │ foo.dev.example.internal
  ▼
127.0.0.1:8443
  │
  │ SSM
  ▼
EC2
  │
  │ ALB:443
  ▼
ALB
```

という形です。

つまり、

### DNS

```text
foo.dev.example.internal → 127.0.0.1
```

### SSM

```text
localhost:8443
    ↓
EC2
    ↓
ALB:443
```

です。

ここで**Chromeの名前解決だけをローカルDNSで127.0.0.1に向ける**ことができれば、かなり綺麗です。

そしてあなたの環境では、**既にローカルDNSを管理しているUbuntu Serverがある**。

これが非常に大きいです。

---

# つまり、Chromeのhost-rulesより既存DNSを使える

最初におっしゃっていた、

> オンプレではローカルDNSを立てて、k8sクラスタにワイルドカードサブドメインを使ってingressしていた

という環境が既にあるので、

```text
Chrome
  │
  │ DNS query
  ▼
UbuntuのローカルDNS
  │
  ├─ *.dev.local
  │       ↓
  │   127.0.0.1
  │
  └─ その他
          ↓
      イントラDNS
```

とできます。

そうするとChrome側には何も細工しなくていい。

これは**今回の目的にはChrome `--host-rules`よりずっと自然**です。

## 最終的な試験構成

私ならまずこれを試します。

```text
                   イントラ
┌──────────────────────────────────────────┐

  ┌──────────────┐
  │ Windows VM   │
  │ Chrome       │
  └──────┬───────┘
         │
         │ DNS
         ▼
  ┌──────────────────┐
  │ Ubuntu DNS       │
  │                  │
  │ *.dev.local      │
  │      ↓           │
  │ 127.0.0.1        │
  └──────────────────┘

         Chrome
           │
           │ https://foo.dev.local:8443
           ▼
      localhost:8443
           │
           │ SSM Port Forward
           ▼

================ AWS VPC ===================

         EC2
           │
           │ TCP 443
           ▼
    Internet-facing ALB
           │
           │ Host/SNI:
           │ foo.dev.local
           ▼
    NGINX Ingress
           │
           ▼
         Envoy
           │
       ┌───┴────┐
       ▼        ▼
      GUI    Tentnas

=============================================
```

これなら、**オンプレ環境との比較としてかなり意味のある実験**になります。

そして、

> ALB → NGINX Ingress → Envoy → GUI/Tentnas

という本来のAWS側アーキテクチャを壊さずに、**SSMだけを「イントラからAWSへの入口」として使う**ことができます。

この構成で次に詰めるべきなのは、**「ローカルDNSを `127.0.0.1` に向けるのか」「SSMのRemoteHostに何を指定するか」「Internet-facing ALBへVPC内EC2から到達させる方法」**の3点です。ここは実際のAWSネットワーク構成次第で少し変わります。
