実運用を意識するなら、単に `Gateway` と `HTTPRoute` を置くだけでなく、

* `Deployment`
* `Service`
* `ServiceAccount`
* `ConfigMap`
* `Gateway`
* `HTTPRoute`
* TLS
* `NetworkPolicy`
* Pod security context
* probes
* resources
* HPA
* PDB
* topology spread
* Helmの `values.yaml` による環境差分
* Gateway API / NGINX Gateway Fabric固有設定の分離

あたりまで考えておくと扱いやすい。

今回は **「1つのWebアプリをNGINX Gateway Fabric経由で公開する」** という想定で、実際にChartとして使える形にしてみる。

なお、NGINX Gateway FabricはGateway APIを利用するので、`Gateway` / `HTTPRoute` 自体はNGF専用APIではなくGateway APIのリソース。NGF固有機能を使うところだけNGF固有リソース・設定に寄せる、という設計にするのがおすすめ。

```text
my-app/
├── Chart.yaml
├── values.yaml
├── values-prod.yaml
├── values-staging.yaml
├── templates/
│   ├── _helpers.tpl
│   ├── _pod.tpl
│   │
│   ├── serviceaccount.yaml
│   ├── configmap.yaml
│   ├── secret.yaml
│   │
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── hpa.yaml
│   ├── pdb.yaml
│   ├── networkpolicy.yaml
│   │
│   ├── gateway.yaml
│   ├── httproute.yaml
│   └── servicemonitor.yaml
│
└── charts/
```

ポイントは、

```text
アプリケーション層
    Deployment
    Service
        ↓
Gateway API層
    HTTPRoute
        ↓
    Gateway
        ↓
NGINX Gateway Fabric
```

という責務分離。

特に **GatewayそのものをアプリChartに含めるかどうか** は運用上かなり重要。

```yaml

kind: Deployment
metadata:
  name: {{ include "my-app.fullname" . }}
  labels:
    {{- include "my-app.labels" . | nindent 4 }}

spec:
  {{- if not .Values.autoscaling.enabled }}
  replicas: {{ .Values.replicaCount }}
  {{- end }}

  revisionHistoryLimit: 3

  selector:
    matchLabels:
      {{- include "my-app.selectorLabels" . | nindent 6 }}

  template:
    metadata:
      labels:
        {{- include "my-app.selectorLabels" . | nindent 8 }}
      {{- with .Values.podLabels }}
        {{- toYaml . | nindent 8 }}
      {{- end }}

      {{- with .Values.podAnnotations }}
      annotations:
        {{- toYaml . | nindent 8 }}
      {{- end }}

    spec:
      serviceAccountName: {{ include "my-app.serviceAccountName" . }}
      automountServiceAccountToken: {{ .Values.serviceAccount.automount }}

      terminationGracePeriodSeconds: {{ .Values.terminationGracePeriodSeconds }}

      imagePullSecrets:
        {{- toYaml . | nindent 8 }}
      {{- end }}

      securityContext:
        {{- toYaml .Values.podSecurityContext | nindent 8 }}

            - name: http
              containerPort: {{ .Values.container.port }}
              protocol: TCP

          securityContext:
            {{- toYaml .Values.securityContext | nindent 12 }}

          {{- with .Values.env }}
          env:
            {{- toYaml . | nindent 12 }}
          {{- end }}

          {{- with .Values.envFrom }}
          envFrom:
            {{- toYaml . | nindent 12 }}
          {{- end }}

          resources:
            {{- toYaml .Values.resources | nindent 12 }}

              {{- include "my-app.selectorLabels" . | nindent 14 }}

        {{- toYaml . | nindent 8 }}
      {{- end }}

        {{- toYaml . | nindent 8 }}
```

# 9. Gateway

ここが今回の本題。

`templates/gateway.yaml`

```yaml
{{- if .Values.gateway.enabled }}
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: {{ default (include "my-app.fullname" .) .Values.gateway.name }}
  labels:
    {{- include "my-app.labels" . | nindent 4 }}

spec:
  gatewayClassName: {{ .Values.gateway.className }}

  listeners:
    - name: {{ .Values.gateway.listener.name }}
      protocol: {{ .Values.gateway.listener.protocol }}
      port: {{ .Values.gateway.listener.port }}

      {{- if .Values.gateway.hostname }}
      hostname: {{ .Values.gateway.hostname | quote }}
      {{- end }}

      {{- if .Values.gateway.tls.enabled }}
      tls:
        mode: Terminate
        certificateRefs:
          - kind: Secret
            name: {{ .Values.gateway.tls.secretName }}
      {{- end }}

      allowedRoutes:
        namespaces:
          from: Same
{{- end }}
```

ここで、

```yaml
gatewayClassName: nginx
```

としている。

これは **NGINX Gateway Fabricが提供しているGatewayClassを使う**という意味。

# 10. HTTPRoute

`templates/httproute.yaml`

```yaml
{{- if and .Values.gateway.enabled .Values.httpRoute.enabled }}
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: {{ include "my-app.fullname" . }}
  labels:
    {{- include "my-app.labels" . | nindent 4 }}

spec:
  parentRefs:
    - name: {{ default (include "my-app.fullname" .) .Values.gateway.name }}

  {{- if .Values.gateway.hostname }}
  hostnames:
    - {{ .Values.gateway.hostname | quote }}
  {{- end }}

  rules:
    - matches:
        - path:
            type: {{ .Values.httpRoute.pathType }}
            value: {{ .Values.httpRoute.path | quote }}

      backendRefs:
        - name: {{ include "my-app.fullname" . }}
          port: {{ .Values.httpRoute.backend.port }}

      timeouts:
        request: {{ .Values.httpRoute.timeout }}
{{- end }}
```

これで、

```text
Internet
    │
    ▼
NGINX Gateway Fabric
    │
    ▼
Gateway
    │
    ▼
HTTPRoute
    │
    ▼
my-app Service
    │
    ▼
Deployment
    │
    ├── Pod
    └── Pod
```

という構成になる。

# 14. TLS対応

productionではHTTPだけではなく、

```yaml
gateway:
  enabled: true

  className: nginx

  hostname: app.example.com

  listener:
    name: https
    protocol: HTTPS
    port: 443

  tls:
    enabled: true
    secretName: app-example-com-tls
```

とする。

するとGatewayは概念的に、

```yaml
listeners:
  - name: https
    protocol: HTTPS
    port: 443
    hostname: app.example.com
    tls:
      mode: Terminate
      certificateRefs:
        - name: app-example-com-tls
```

となる。

# 15. ただし「GatewayをアプリChartに入れる」は少し注意

ここが実運用ではかなり重要。

例えば複数アプリがあるとして、

```text
                ┌── app-a
Internet ── Gateway ── HTTPRoute
                │
                ├── app-b
                │
                └── app-c
```

という構成なら、

```text
gateway.yaml
```

を各アプリChartに入れるのはあまりおすすめしない。

むしろ、

```text
gateway-infra/
├── Chart.yaml
└── templates/
    └── gateway.yaml

app-a/
├── Chart.yaml
└── templates/
    └── httproute.yaml

app-b/
├── Chart.yaml
└── templates/
    └── httproute.yaml
```

のように分離する。

つまり、

**GatewayはインフラChart、HTTPRouteはアプリChart**

という考え方。

# 16. その場合の構成

かなり実運用っぽくすると、

```text
Helm
│
├── gateway-infra
│   │
│   └── Gateway
│       └── listener :443
│
├── frontend
│   │
│   ├── Deployment
│   ├── Service
│   └── HTTPRoute
│
├── api
│   │
│   ├── Deployment
│   ├── Service
│   └── HTTPRoute
│
└── admin
    │
    ├── Deployment
    ├── Service
    └── HTTPRoute
```

例えば、

```text
https://example.com/
        ↓
HTTPRoute frontend
        ↓
frontend Service

https://example.com/api
        ↓
HTTPRoute api
        ↓
api Service

https://example.com/admin
        ↓
HTTPRoute admin
        ↓
admin Service
```

となる。

これはかなり綺麗。

# 17. さらに一歩進めるなら

`app` Chart側はGatewayを作らず、

```yaml
httpRoute:
  enabled: true

  parentRefs:
    - name: shared-gateway
      namespace: gateway-system

  hostnames:
    - app.example.com

  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /

      backendRefs:
        - name: my-app
          port: 8080
```

という形にする。

すると、

```yaml
spec:
  parentRefs:
    - name: shared-gateway
      namespace: gateway-system
```

で共通Gatewayに接続できる。

この設計のほうが、**「アプリをデプロイしたら勝手にインターネット向けGatewayまで作られる」**という危険な状態を避けられる。

# 18. production向けの最終構成なら

自分なら最終的にはこうする。

```text
helm/
│
├── gateway-infra/
│   ├── Chart.yaml
│   ├── values.yaml
│   └── templates/
│       ├── gatewayclass.yaml       # 必要な場合のみ
│       ├── gateway.yaml
│       └── certificate.yaml        # cert-managerを使うなら
│
└── my-app/
    ├── Chart.yaml
    ├── values.yaml
    ├── values-staging.yaml
    ├── values-prod.yaml
    │
    └── templates/
        ├── _helpers.tpl
        ├── serviceaccount.yaml
        ├── configmap.yaml
        ├── deployment.yaml
        ├── service.yaml
        ├── httproute.yaml
        ├── hpa.yaml
        ├── pdb.yaml
        └── networkpolicy.yaml
```

そして責務を、

```text
gateway-infra
    ↓
「外からどう入ってくるか」

my-app
    ↓
「このアプリへどうルーティングするか」

Deployment / Service
    ↓
「アプリをどう動かすか」
```

と分ける。

これが個人的には一番おすすめ。

特にNGINX Gateway Fabricを使うなら、**Ingressの代替としてGatewayを各アプリChartにベタ書きするより、「共有Gateway + アプリごとのHTTPRoute」にする**と、Gateway APIのメリットがかなり活きてくる。

もし次に進めるなら、**`cert-manager + NGINX Gateway Fabric + shared Gateway + 複数HTTPRoute + Helm`** まで含めた構成にすると、かなり実際のproduction Kubernetes構成に近くなる。
