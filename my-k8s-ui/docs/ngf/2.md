うん。この構成なら、**「Gatewayはインフラ側で1つだけ管理し、各アプリはHTTPRouteだけを追加する」**形にするのがかなり実運用向き。

全体像はこんな感じ。

```text
                         Internet
                            │
                            │ HTTPS :443
                            ▼
              ┌──────────────────────────┐
              │ NGINX Gateway Fabric      │
              │                           │
              │ GatewayClass: nginx       │
              └────────────┬─────────────┘
                           │
                           ▼
              ┌──────────────────────────┐
              │ shared-gateway            │
              │ namespace: gateway-system │
              │                           │
              │ HTTPS :443                │
              │ *.example.com             │
              │                           │
              │ TLS Secret                │
              └────────────┬─────────────┘
                           │
              ┌────────────┼─────────────┐
              │            │             │
              ▼            ▼             ▼
         HTTPRoute     HTTPRoute     HTTPRoute
         frontend      api           admin
              │            │             │
              ▼            ▼             ▼
         frontend-svc   api-svc      admin-svc
              │            │             │
             Pods         Pods          Pods

                     ▲
                     │
              cert-manager
                     │
              Let's Encrypt
```

ここでは、

* `gateway-system` → Gatewayインフラ
* `cert-manager` → TLS証明書
* `frontend` → frontendアプリ
* `api` → APIアプリ
* `admin` → adminアプリ

というnamespace構成にする。

# 3. Gatewayのvalues.yaml

```yaml
gateway:
  name: shared-gateway

  namespace: gateway-system

  className: nginx

  hostname: "*.example.com"

  listener:
    name: https
    protocol: HTTPS
    port: 443

  enabled: true

  secretName: wildcard-example-com-tls

  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer

    # - example.com
```

ここで重要なのが、


の部分。

# 4. Gateway

`templates/gateway.yaml`

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway

metadata:
  name: {{ .Values.gateway.name }}
  namespace: {{ .Values.gateway.namespace }}

spec:
  gatewayClassName: {{ .Values.gateway.className }}

  listeners:
    - name: {{ .Values.gateway.listener.name }}

      protocol: {{ .Values.gateway.listener.protocol }}

      port: {{ .Values.gateway.listener.port }}

      hostname: {{ .Values.gateway.hostname | quote }}

      tls:
        mode: Terminate

        certificateRefs:
          - kind: Secret
            name: {{ .Values.gateway.tls.secretName }}

      allowedRoutes:
        namespaces:
          from: All
```

これで、

```text
Gateway
 └── HTTPS :443
       │
       ├── *.example.com
       │
       └── TLS termination
```

をGateway側で担当する。

---

# 5. `allowedRoutes` はかなり重要

ここでは、

```yaml
allowedRoutes:
  namespaces:
    from: All
```

としている。

つまり、

```text
frontend namespace
api namespace
admin namespace
```

など、別namespaceからでもこのGatewayを参照できる。

ただしproductionでは、**本当にAllでいいのか**は検討した方がいい。

例えば特定namespaceだけ許可する設計にするなら、Gateway APIのnamespace selectorを使う。

ただし、その場合はnamespaceにラベルを付けるなどの運用が必要。

例えば、

```yaml
allowedRoutes:
  namespaces:
    from: Selector
    selector:
      matchLabels:
        gateway-access: "true"
```

として、

```text
frontend namespace
  gateway-access=true

api namespace
  gateway-access=true
```

のようにする。

これはproductionではかなり有効。

# 7. ClusterIssuer

これはGateway Chartに入れてもいいけど、個人的にはさらに分離する。

```text
cert-manager
    ↓
ClusterIssuer

gateway-infra
    ↓
Certificate
    ↓
Gateway
```

例えばClusterIssuerは、

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer

metadata:
  name: letsencrypt-prod

spec:
  acme:
    email: admin@example.com

    server: https://acme-v02.api.letsencrypt.org/directory

    privateKeySecretRef:
      name: letsencrypt-prod

    solvers:
      - dns01:
          cloudflare:
            apiTokenSecretRef:
              name: cloudflare-api-token-secret
              key: api-token
```

のような形。

ここはDNSプロバイダによって変わる。

例えばRoute53ならAWS IAM/IRSA、CloudflareならAPI Token、AzureならAzure DNS、といった感じ。

# 8. Certificate

Gateway Chartの

```text
templates/certificate.yaml
```

を、

```yaml
{{- if .Values.certificate.enabled }}
apiVersion: cert-manager.io/v1
kind: Certificate

metadata:
  name: {{ .Values.certificate.secretName }}
  namespace: {{ .Values.gateway.namespace }}

spec:
  secretName: {{ .Values.certificate.secretName }}

  issuerRef:
    name: {{ .Values.certificate.issuerRef.name }}
    kind: {{ .Values.certificate.issuerRef.kind }}

  dnsNames:
    {{- toYaml .Values.certificate.dnsNames | nindent 4 }}
{{- end }}
```

とする。

すると、

```text
Certificate
    │
    │ cert-manager
    ▼
wildcard-example-com-tls
    │
    │ Secret
    ▼
Gateway
```

になる。

---

# 9. ここで一つ注意

Wildcard certificate、

```text
*.example.com
```

をLet's Encryptで取得する場合、基本的にHTTP-01ではなく**DNS-01 challenge**を使う。

だから、

```text
Internet
   │
   └── HTTP-01
```

ではなく、

```text
cert-manager
     │
     ▼
DNS Provider
     │
     ▼
_acme-challenge.example.com
```

という構成になる。

そのため、productionではDNS providerとの連携方法をきちんと設計する。

# 11. FrontendのHTTPRoute

`templates/httproute.yaml`

```yaml
{{- if .Values.httpRoute.enabled }}

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute

metadata:
  name: {{ include "frontend.fullname" . }}

spec:
  parentRefs:
    - name: {{ .Values.httpRoute.gateway.name }}
      namespace: {{ .Values.httpRoute.gateway.namespace }}

  hostnames:
    {{- toYaml .Values.httpRoute.hostname | nindent 4 }}

  rules:
    - matches:
        - path:
            type: {{ .Values.httpRoute.pathType }}
            value: {{ .Values.httpRoute.path }}

      backendRefs:
        - name: {{ include "frontend.fullname" . }}
          port: {{ .Values.service.port }}

{{- end }}
```

これで、

```text
https://www.example.com/
             │
             ▼
      shared-gateway
             │
             ▼
      frontend HTTPRoute
             │
             ▼
      frontend Service
```

となる。

例えば、


にしたい場合。

```text

     │

     │

```

API側：

```yaml
spec:
  parentRefs:
    - name: shared-gateway
      namespace: gateway-system

        - path:
            type: PathPrefix
            value: /api

      backendRefs:
        - name: api
          port: 8080
```

Admin：

```yaml
spec:
  parentRefs:
    - name: shared-gateway
      namespace: gateway-system

  hostnames:
    - example.com

    - matches:
        - path:
            type: PathPrefix
            value: /admin

      backendRefs:
        - name: admin
          port: 8080
```

これがGateway APIのかなり美味しいところ。

# 15. Gatewayを1個にする理由

例えば昔ながらのIngress構成だと、

```text
frontend Ingress
api Ingress
admin Ingress
```

と作ることが多い。

Gateway APIなら、

```text
                    Gateway
                       │
          ┌────────────┼────────────┐
          │            │            │
     HTTPRoute     HTTPRoute    HTTPRoute
      frontend        api          admin
```

とできる。

つまり、

**インフラチームがGatewayを管理し、アプリチームがHTTPRouteを管理する**

という責務分離ができる。

これはHelm/GitOpsとも非常に相性がいい。

# 18. Gateway側でやること / HTTPRoute側でやること

ここを明確にしておくとChart設計が崩れにくい。

| 項目                  | Gateway       | HTTPRoute |
| ------------------- | ------------- | --------- |
| Load Balancer       | ✅             |           |
| Port 443            | ✅             |           |
| TLS termination     | ✅             |           |
| Certificate         | Certificate経由 |           |
| Host                | △             | ✅         |
| Path routing        |               | ✅         |
| Backend Service     |               | ✅         |
| Timeout             |               | ✅         |
| Header manipulation |               | ✅         |
| Traffic splitting   |               | ✅         |
| アプリ固有ルーティング         |               | ✅         |

つまり、

> **Gateway = 「入口」**

> **HTTPRoute = 「どのアプリにどう振るか」**

と覚えておけばいい。

# 19. Traffic splittingもHTTPRoute側

Gateway APIを使うメリットとして、例えばBlue/GreenやCanaryもHTTPRouteで表現できる。

```yaml
rules:
  - backendRefs:
      - name: api-v1
        port: 8080
        weight: 90

      - name: api-v2
        port: 8080
        weight: 10
```

すると、

```text
             HTTPRoute
                 │
        ┌────────┴────────┐
        │                 │
      90%               10%
        │                 │
        ▼                 ▼
     api-v1             api-v2
```

という構成にできる。

Helm valuesに、

```yaml
httpRoute:
  backendRefs:
    - name: api-v1
      port: 8080
      weight: 90

    - name: api-v2
      port: 8080
      weight: 10
```

と持たせれば、デプロイ時に変更できる。

# 21. もう一つ重要なポイント：GatewayとCertificateを同じChartにするか

自分なら、

```text
platform/
├── cert-manager
├── cert-manager-config
│   └── ClusterIssuer
│
└── gateway-infra
    ├── Gateway
    └── Certificate
```

くらいに分ける。

理由は、

```text

```

は**クラスタ全体のインフラ**だから。

一方、

```text

```

は**そのGatewayで使う証明書**なのでGateway側に近い。

つまり、

```text
cert-manager
    ↓
ClusterIssuer
    ↓
Certificate
    ↓
Secret
    ↓
Gateway
```

という責務になる。

最終的にはこんな感じがかなり綺麗。

```text
Kubernetes Cluster
│
├── cert-manager
│   │
│   ├── cert-manager
│   └── ClusterIssuer
│       └── letsencrypt-prod
│
├── gateway-system
│   │
│   ├── NGINX Gateway Fabric
│   │
│   ├── Gateway
│   │   └── shared-gateway
│   │       └── :443
│   │
│   └── Certificate
│       └── wildcard-example-com-tls
│
├── frontend
│   │
│   ├── Deployment
│   ├── Service
│   └── HTTPRoute
│       └── www.example.com
│
├── api
│   │
│   ├── Deployment
│   ├── Service
│   └── HTTPRoute
│       └── api.example.com
│
└── admin
    │
    ├── Deployment
    ├── Service
    └── HTTPRoute
        └── admin.example.com
```

通信としては、

```text
                     Let's Encrypt
                          ▲
                          │ ACME
                          │
Internet ──HTTPS──> NGINX Gateway Fabric
                          │
                          ▼
                  ┌───────────────┐
                  │ shared-gateway│
                  │ TLS terminate │
                  └───────┬───────┘
                          │
             ┌────────────┼────────────┐
             │            │            │
             ▼            ▼            ▼
        frontend-route api-route  admin-route
             │            │            │
             ▼            ▼            ▼
        frontend-svc   api-svc    admin-svc
             │            │            │
             ▼            ▼            ▼
           Pods         Pods         Pods
```

この構成なら、**Gatewayの変更とアプリのリリースを独立させられる**のがかなり大きい。

例えばAPIをリリースするときは、

```bash
helm upgrade api ./charts/api \
  --namespace api \
  --values values-prod.yaml
```

だけで済み、共有Gatewayには触らない。

逆にTLS証明書やLB設定を変更するときは、

```bash
helm upgrade gateway-infra ./charts/gateway-infra \
  --namespace gateway-system \
  --values values-prod.yaml
```

だけでいい。

## そして、実際に作るならもう一段おすすめの形

ここまでの例をさらに整理して、**「アプリChartは1個だけ作り、frontend/api/adminはvaluesだけ変えて3回installする」**構成にするのがいい。

つまり、

```text
charts/
├── gateway-infra/
│
└── app/
    ├── templates/
    │   ├── deployment.yaml
    │   ├── service.yaml
    │   ├── httproute.yaml
    │   ├── hpa.yaml
    │   ├── pdb.yaml
    │   └── networkpolicy.yaml
    │
    └── values.yaml

environments/
├── prod/
│   ├── gateway.yaml
│   ├── frontend.yaml
│   ├── api.yaml
│   └── admin.yaml
│
└── staging/
    ├── gateway.yaml
    ├── frontend.yaml
    ├── api.yaml
    └── admin.yaml
```

にする。

そうすると、

```text
app Chart
    │
    ├── frontend values
    ├── api values
    └── admin values
```

で使い回せる。

**実際のプロジェクトとして始めるなら、この「共通app Chart + gateway-infra Chart + cert-manager/ClusterIssuer + prod/staging values」まで含めた完成形にするのが一番おすすめ。**
