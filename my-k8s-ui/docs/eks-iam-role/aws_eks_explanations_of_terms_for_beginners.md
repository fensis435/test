# EKS構築 事前確認事項の解説(初心者向け)

Oct 24, 2026 · @xyz

## 全体像

権限をもらうだけではEKS構築は始められません。管理者から情報をもらい、管理者にしかできない作業を先にやってもらう必要があり、その一覧が Excel の「確認事項」シートです。

注記: 依頼のあった「事前確認」という名前のシートは Excel に存在せず、内容が一致する「確認事項」シート(権限以外に管理者から入手する情報と事前作業)の11項目を解説しています。

準備は次の3種類に分かれます。後回しにすると、構築の途中で権限エラーやルール違反で止まり、やり直しになります。

- 管理者しか知らない情報をもらう(VPC ID、既存SGなど)
- 管理者にしかできない作業をしてもらう(境界ポリシー、サービスリンクロールなど)
- 社内ルールや制限を事前に知る(SCP、タグポリシー、クォータなど)

## 1. 既存VPC情報

**確認すること:** VPC ID、未使用のCIDR、NAT GatewayのID、AZ(アベイラビリティゾーン)の構成。

**わかりやすく言うと:** VPCはAWS上の自社専用ネットワーク空間です。今回は既存サービスが動くVPCに、新しいサブネット(ネットワークの区画)を2つ足します。

- **VPC ID** は、そのVPCを指定する番号です。
- **未使用CIDR** は、既存のIPアドレスとかぶらない空き範囲です。かぶると通信が壊れるため、空きを教えてもらいます。
- **NAT Gateway ID** は、プライベートなサブネットからインターネット(パッケージ取得など)へ出る出口です。新サブネットのルート設定で指定します。
- **AZ構成** は、データセンターの区画の構成です。障害に備えて複数AZに分けて置くため、既存の使い方を知る必要があります。

**なぜ必要か:** サブネットとルートの設計ができないためです。

## 2. 既存backendのSG ID

**確認すること:** 既存backendに付いているセキュリティグループ(SG)のID。

**わかりやすく言うと:** SGは、サーバやロードバランサの前に立つ「通信の門番(ファイアウォール)」です。「この相手からのこの通信だけ通す」というルールを書きます。

**なぜ必要か:** 新サービスの入口(NLB)のSGに、「既存backendからの通信だけ許可する」というルールを書くためです。相手はIPアドレスではなく、そのSG IDで指定します。

**補足:** 既存SGを変更する権限は不要で、IDを参照するだけで済みます。既存システムに触れないので、管理者にも頼みやすい項目です。

## 3. 境界ポリシー(Permissions Boundary)

**確認すること:** 境界ポリシーの名前と内容。

**わかりやすく言うと:** 開発者に「IAMロールを作る権限」を渡すと、理屈の上では自分より強い権限のロールを作って自分に付けられてしまいます。これを防ぐため、「作るロールの権限はこの範囲を超えてはいけない」という上限を決めるのが境界ポリシーです。ロールにかぶせる「天井」と考えてください。

**なぜ必要か:** 権限一覧の2-4(IAM)は、「境界ポリシーが付いたロールだけ作成できる」という条件付きで申請しています。管理者側でポリシーを用意し、名前を教えてもらう必要があります。管理者にとっても安心材料になり、承認されやすくなります。

## 4. サービスリンクロール(SLR)

**確認すること:** 管理者に事前作成してもらえるか。

**わかりやすく言うと:** サービスリンクロールは、EKSやRDSなどのAWSサービスが、他のリソースを操作するために使う専用ロールです。アカウント内でそのサービスを初めて使うときに、1回だけ作られます。

**なぜ必要か:** 初回作成には `iam:CreateServiceLinkedRole` という権限を開発者に渡す必要があります。管理者に先に作ってもらえば、この権限を渡さずに済み、申請する権限が減ります。

## 5. KMSキーの扱い

**確認すること:** KMSキーを開発者が作るのか、管理者が作るのか。

**わかりやすく言うと:** KMSは、データを暗号化するための「鍵」を管理するサービスです。今回はEKSのSecrets、EBS、EFS、RDS、S3、CloudWatch Logsなど、ほぼすべての保存データをこの鍵で暗号化する前提です(概要シートに記載)。

**なぜ必要か:** 鍵を自分たちで作る場合は、KMSの作成権限(権限一覧2-6)が必要です。管理者が作ってくれる場合は、「その鍵を使う権限」だけ申請すれば済みます。どちらになるかで申請範囲が変わります。

## 6. AssumeRoleの信頼設定

**確認すること:** 踏み台EC2のロールから、開発者Roleに切り替えられる設定。

**わかりやすく言うと:** AssumeRoleは、別のロールの権限を一時的に借りる仕組みです。手順③では、踏み台EC2に付けたロールで入り、そこから「開発者Role」に切り替えてEKSの設定作業をします。入場券を段階的に持ち替えるイメージです。

**なぜ必要か:** 切り替え先(開発者Role)側に、「この踏み台のロールからの切り替えを許可する」という信頼設定が必要です。これがないと、手順③の入口で止まります。

## 7. ネットワーク

**確認すること:** 社内イントラネットからAWSのAPIへ届く経路と、プロキシの有無。

**わかりやすく言うと:** 作業は社内のPCやサーバから、AWS CLI、CloudFormation、SSMなどのAWSサービスにつないで行います。会社によっては、外部への通信が制限されていたり、プロキシ(中継サーバ)経由でしか出られなかったりします。

**なぜ必要か:** 権限が完璧でも、通信が届かなければ何もできません。プロキシがある場合は、そのアドレスや認証方法を事前に聞いておく必要があります。

## 8. SCP / リージョン制限

**確認すること:** 使えるリージョンと、禁止されているAPI。

**わかりやすく言うと:** SCP(サービスコントロールポリシー)は、組織(Organizations)全体にかかる「全社共通の禁止ルール」です。たとえば「東京リージョン以外は使用禁止」「このサービスは使用禁止」といった制限です。重要なのは、個人にいくら権限を付けても、SCPで禁止されたことはできない点です。

**なぜ必要か:** 申請して許可が出たのに、実行したら拒否される、という事態を防ぐためです。

## 9. クォータ

**確認すること:** EIP、vCPU、セキュリティグループ数などの上限(AWSが決める利用上限)。

**わかりやすく言うと:** AWSには、サービスごとに「1アカウントで使える数の上限」があります。

- **EIP:** 固定のパブリックIPアドレスです。
- **vCPU:** EC2で使える計算能力の合計です。
- **SG数:** 作れるセキュリティグループの数です。

**なぜ必要か:** Karpenterは、負荷に応じて自動でEC2を増やします。vCPUの上限が低いと、増やそうとした瞬間にエラーになります。既存サービスがすでに枠を使っている可能性もあるため、空き枠の確認が必要です。

## 10. タグポリシー

**確認すること:** 必須とされているタグ。

**わかりやすく言うと:** タグは、リソースに付ける「名札」です(例: `Project=myproj`、`Owner=xxx`、`CostCenter=123`)。会社によっては、「このタグが付いていないリソースは作成できない」というルールがあります。

**なぜ必要か:** CFNテンプレートに最初から必須タグを入れておけば、タグ不足による作成失敗を避けられます。権限を `myproj-*` のようなタグや名前で絞る設計ともつながるため、タグ名の確認は重要です。

## 11. ローカル環境

**確認すること:** 作業者のPCやサーバに、AWS CLI v2とSession Manager Pluginが入っているか。

**わかりやすく言うと:**

- **AWS CLI v2** は、コマンドでAWSを操作するツールです。
- **Session Manager Plugin** は、SSMを通して踏み台EC2にログインしたり、ポートフォワード(手元のPCのポート経由で、EKS内のメンテナンスWebUIを見る)をしたりするための部品です。

**なぜ必要か:** 今回は踏み台へSSHではなくSSMでログインします。そのため、WindowsのPCとLinuxサーバの両方にこのプラグインが必要です。ないと踏み台に入れず、メンテナンスUIも見られません。

## 優先して確認すべき4項目

次の4つは権限申請の中身そのものを左右するため、最初に管理者へ聞くと手戻りが減ります。それ以外は構築準備と並行して確認できます。

1. 境界ポリシー(項目3)
2. 既存VPC情報(項目1)
3. SCP / リージョン制限(項目8)
4. AssumeRoleの信頼設定(項目6)

「申請段階」シートの第1弾(踏み台とEKS本体、2-1〜2-7)に着手する前に、この4つが揃っていると安心です。
