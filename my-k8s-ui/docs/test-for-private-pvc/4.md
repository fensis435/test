はい。それなら構成がかなり明確になります。
`alb.ingress.kubernetes.io/target-type: ip` を使う予定なら、**AWS Load Balancer ControllerがALBを作り、ALBのTarget GroupにNGINX Ingress ControllerのPod IPを直接登録する**構成になります。

つまり予定しているのは、厳密にはこうです。

```text
Windows VM / Chrome
        │
        │ DNS
        ▼
Ubuntu / dnsmasq
        │
        │ SSM port forwarding
        ▼
   Bastion EC2
        │
        │ HTTPS :443
        ▼
┌───────────────────────┐
│ Internal ALB          │
│                       │
│ Listener :443         │
└──────────┬────────────┘
           │
           │ Target Group
           │ target-type = ip
           ▼
┌───────────────────────┐
│ NGINX Ingress Pod     │
│ :443                  │
└──────────┬────────────┘
           │
           ▼
        Envoy
           │
       ┌───┴────┐
       ▼        ▼
      GUI    Tentnas
```

これは今回の試験にはかなり良い構成です。

# 重要：ALBとNGINXの役割

ここでは役割を分けて考えると分かりやすいです。

### ALB

AWS側の入口です。

```text
TLS
WAF
Health Check
```

などを担当。

### NGINX Ingress

Kubernetes側のHTTPルーティングです。

例えば、

```text
foo.dev.example.internal
        ↓
foo Service

bar.dev.example.internal
        ↓
bar Service
```

を担当します。

つまり、

```text
ALB
 ↓
NGINX
 ↓
Ingress Rule
 ↓
Service
```

です。

---

# `target-type: ip` の意味

ここが今回かなり重要です。

例えばNGINX Ingress Serviceを、

```yaml
apiVersion: v1
kind: Service
metadata:
  name: ingress-nginx-controller
  namespace: ingress-nginx
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-nlb-target-type: ip
```

という話ではなく、**AWS Load Balancer Controllerが管理するIngress**として、

```yaml
metadata:
  annotations:
    alb.ingress.kubernetes.io/target-type: ip
```

を指定する場合です。

この場合、ALBのTarget Groupには、

```text
NGINX Pod IP
```

が直接登録されます。

例えば、

```text
10.0.10.21
10.0.10.22
```

のようなPod IPです。

NodePortを経由しません。

---

# ただし、ここで一つ注意

今回、

```text
ALB
 ↓
NGINX Ingress
```

にしたいなら、**ALBを作るIngressと、NGINX IngressのIngressは別物**として考えた方がよいです。

AWS Load Balancer Controllerに、

```yaml
kind: Ingress
```

を渡すと、そのIngress自体がALBのルーティング設定になります。

一方、NGINX Ingress Controllerにも、

```yaml
kind: Ingress
```

を渡します。

したがって、例えば：

```text
                 Kubernetes
                     │
          ┌──────────┴──────────┐
          │                     │
AWS LB Controller          NGINX Controller
          │                     │
          ▼                     ▼
       ALB                 Ingress Rules
          │                     │
          └───────→ NGINX Pod ←─┘
```

という二段階になります。

---

# 今回の用途ならALBはL4的に使うのが綺麗

例えばALB側で、

```text
*:443
   ↓
NGINX Ingress Pod
```

とする。

そして**実際のHostベースルーティングはNGINXに任せる**。

```text
foo.dev.local
    ↓
NGINX
    ↓
foo-service

bar.dev.local
    ↓
NGINX
    ↓
bar-service
```

という構成です。

ただしALBはL7なので、完全なL4プロキシにはなりません。ALB自身もHTTP/HTTPSレベルの処理をします。

---

# HTTPSをどこで終端するか

ここは最初に決めた方がいいです。

## パターン1：ALBでTLS終端

```text
Chrome
  │ HTTPS
  ▼
ALB
  │ HTTP
  ▼
NGINX
```

ALBにACM証明書を設定します。

この場合、

```text
foo.dev.local
```

のTLSはALBで終わります。

---

## パターン2：ALB → NGINXもHTTPS

```text
Chrome
  │ HTTPS
  ▼
ALB
  │ HTTPS
  ▼
NGINX
```

こちらならNGINXにも証明書が必要です。

---

今回の**お試し**なら、まずは **ALBでTLS終端**が簡単です。

```text
Chrome
  │ HTTPS
  ▼
ALB :443
  │ HTTP :80
  ▼
NGINX
```

そしてNGINXではHostを見て、

```text
foo.dev.local → foo-service
bar.dev.local → bar-service
```

とします。

---

# ただし「元のHost名」はどうなる？

ALBがHTTP/HTTPSを処理した後も、通常はHostヘッダをバックエンドへ渡します。

つまり、

```http
Host: foo.dev.local
```

を維持してNGINXへ渡せます。

したがって、

```text
Chrome
  │
  │ Host: foo.dev.local
  ▼
ALB
  │
  │ Host: foo.dev.local
  ▼
NGINX
```

として、NGINXのIngressルールが使えます。

---

# ここで今回のSSMが効いてくる

最終的には、

```text
Chrome
   │
   │ https://foo.dev.local
   │
   ▼
dnsmasq
   │
   │ → Ubuntu Server
   ▼
Ubuntu:8443
   │
   │ SSM
   ▼
Bastion EC2
   │
   │ HTTPS
   ▼
Internal ALB
   │
   │ HTTP
   ▼
NGINX Pod
   │
   ▼
Envoy
   │
   ▼
GUI
```

です。

**SSMはHTTPを理解しない単純なTCPトンネルなので、Host/SNIをいじらない**のが今回かなり都合がいいところです。

---

# ただし、ALBの「Internal」は今回むしろ正解

前の話とつながります。

今回のALBは、

```yaml
alb.ingress.kubernetes.io/scheme: internal
```

にしておけばいいです。

そして、

```yaml
alb.ingress.kubernetes.io/target-type: ip
```

です。

イメージとしては：

```yaml
metadata:
  annotations:
    alb.ingress.kubernetes.io/scheme: internal
    alb.ingress.kubernetes.io/target-type: ip
```

これで、

```text
Internet
   X
   │
   │
Internal ALB
   │
   ▼
NGINX
```

となります。

今回のアクセス経路はInternetではなく、

```text
イントラ
 ↓
SSM
 ↓
VPC
 ↓
Internal ALB
```

なので、**ALBをInternet-facingにする必要はありません。**

---

# WAFについて

ここだけ、元のお話との関係で注意です。

「最終的にインターネットへ公開するためWAFを使う」という目的なら、

```text
Internet
 ↓
WAF
 ↓
Internet-facing ALB
 ↓
NGINX
```

という本番構成になると思います。

一方、今回の開発環境では、

```text
SSM
 ↓
Internal ALB
 ↓
NGINX
```

でよいでしょう。

WAF自体を今回テストしたいのでなければ、**開発用ALBにWAFを付ける必要はありません**。

## 私ならまずこの最小構成にします

```text
             ┌── Windows VM
             │      Chrome
             │
             │ DNS
             ▼
       Ubuntu / dnsmasq
             │
             │ localhost:8443相当
             ▼
            SSM
             │
             ▼
       Bastion EC2
             │
             │ :443
             ▼
     ┌─────────────────┐
     │ Internal ALB    │
     │ AWS LB Controller
     └────────┬────────┘
              │
              │ target-type: ip
              ▼
       NGINX Pod × 2
              │
              ▼
            Envoy
              │
          ┌───┴───┐
          ▼       ▼
         GUI   Tentnas
```

そしてDNSは、

```text
foo.dev.local → Ubuntu Server
bar.dev.local → Ubuntu Server
```

だけ。

Kubernetes側は、

```text
foo.dev.local → foo Service
bar.dev.local → bar Service
```

をNGINX Ingressで設定。

これなら、**あなたのオンプレ環境の「ローカルDNS + ワイルドカード + Ingress」という仕組みを、AWS側ではほぼそのまま再現して試せます。**

なお、NGINX Ingress Controllerをまだインストールしていないのであれば、次にやるなら **「EKSにNGINX Ingressを入れる → AWS Load Balancer ControllerでInternal ALBを作る → `target-type: ip`でNGINXへ接続する」部分を、Helmコマンド・IAM/IRSA・Security Group・Ingress YAMLまで含めて一式**にすると、実際にそのまま試せる形にできます。
