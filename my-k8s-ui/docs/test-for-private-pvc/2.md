はい。その構成なら、かなり整理できます。
そして重要なのは、**「ALBがEKSクラスタ用のprivate subnetにいる」こと自体は問題ではない**です。ALBはInternet-facingにもInternalにもできますが、**Internet-facing ALBをprivate subnetに置くことはできません**。なので、今のALBが本当にprivate subnetのみに配置されているなら、現状は **Internal ALB** のはずです。

まず現在の構成をこう理解します。

```text
イントラ
  │
  ▼
Windows VM
  │
  │ DNS
  ▼
Ubuntu/KVM Host
  │
  │ SSM
  ▼
AWS VPC
┌──────────────────────────────────────┐
│                                      │
│  Bastion Subnet       VPCE Subnet    │
│       │                    │         │
│       ▼                    │         │
│   EC2 Bastion ◄────────────┘         │
│       │                              │
│       │ TCP                           │
│       ▼                              │
│  EKS Private Subnets                 │
│       │                              │
│       ▼                              │
│  Internal ALB                        │
│       │                              │
│       ▼                              │
│  NGINX Ingress                       │
│       │                              │
│       ▼                              │
│     Envoy                            │
│       │                              │
│    GUI / Tentnas                     │
│                                      │
└──────────────────────────────────────┘
```

この構成なら、**今回の「まず動作確認したい」という目的には、ALBをInternet-facingに変更する必要はありません。**

```text
Chrome

  ▼
127.0.0.1:8443
  │

  ▼
Bastion EC2
  │

  ▼
Internal ALB
  │
  ▼
NGINX
  │

  │
  ▼

```

を試せます。

### ここが今回のポイント

SSMのRemoteHostを**Internal ALBのDNS名**にします。

概念的には、

```text
localPort = 8443
remoteHost = internal-xxxx.ap-northeast-1.elb.amazonaws.com
remotePort = 443
```

です。

すると、

```text
Chrome
  ↓
localhost:8443
  ↓
SSM
  ↓
Bastion EC2
  ↓
Internal ALB:443
```

となります。

そしてChromeが送るHTTPS通信には、

```text
SNI: foo.dev.local
Host: foo.dev.local
```

が入ったままなので、ALB → NGINXまで**元のホスト名を維持したまま**通せます。

---

### ただし1点、DNSについて重要

ここは先ほどの説明を少し修正します。

UbuntuのローカルDNSで、

```text
foo.dev.local → 127.0.0.1
```

とすればよい、という話は、**ChromeがWindows VM上で動いていて、SSMトンネルのlocal endpointもWindows VM上にある場合**です。

今回SSMをどこで実行するかが重要です。

もしUbuntu Server上でSSMを起動するなら、

```text
Chrome (Windows)
   │
   │ foo.dev.local
   ▼
Ubuntu DNS
   │
   ▼
Ubuntu:8443
   │
   ▼
SSM
```

となります。

一方、Windows VM上でSSMクライアントを動かせるなら、

```text
Chrome
   │
   ▼
Windows:8443
   │
   ▼
SSM
```

です。

**「SSMセッションをどのマシンから張るか」**によって、DNSの向け先を決めればよいです。

---

そして今のVPC構成を見る限り、私はまず

**Internal ALBをそのまま利用 → Bastion EC2をRemoteHost到達地点にする → SSM TCP Forward → Chromeのホスト名をローカルDNSで解決**

を試すのがいいと思います。

これならAWS側のネットワークをほとんど変更せずに、オンプレでやっていた

```text
*.dev.local
     ↓
Ingress
     ↓
Service
```

の体験をかなり忠実に再現できます。
