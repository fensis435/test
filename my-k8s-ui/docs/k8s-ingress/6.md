**そのままは使えません。** IngressリソースとGateway API(NGF)のHTTPRouteはリソースモデル自体が別物なので、変換作業が必須です。ただし全部手作業ではなく、変換を自動化するツールがあります。

## なぜそのまま使えないか

- `Ingress` は「1つのリソースにロードバランサ設定とルーティングルールを混在」させる設計、対してGateway APIは `Gateway`(インフラ管理者向け:リスナー/TLS)と `HTTPRoute`(開発者向け:ルーティングルール)に役割分離されています。構造そのものが違うのでYAMLの互換性はありません。
- 従来Ingressの高度な機能(rewrite、rate limiting、CORS、ヘッダー操作)は全てingress-nginx独自のアノテーションに依存していました。これらのアノテーションはGateway APIには存在しないので、機能ごとにHTTPRouteのネイティブフィールドかNGF独自CRDへの置き換えが必要です。

## 変換ツール: ingress2gateway

`ingress2gateway`(v1.0.0、Gateway API SIGのサブプロジェクト)は既存のIngressリソースを読み取ってGateway/HTTPRouteのYAMLを自動生成するツールです。30以上の一般的なingress-nginxアノテーションに対応しています。

```bash
# クラスタの既存Ingressを読み取って変換
ingress2gateway print --providers=ingress-nginx -A > gateway-resources.yaml
```

`rewrite-target`、`ssl-redirect`、`backend-protocol`、`use-regex` などのアノテーションはネイティブなGateway APIフィールドに変換されます。Gateway APIに対応する機能がないアノテーションは、出力YAML内にコメントとして残されるので、手動対応が必要な箇所が分かるようになっています。

ただし注意点として、これは完全な移行ソリューションではなく、変換されたリソースを人手でレビューし、動作確認し、環境固有の追加設定を行う必要がある変換ユーティリティです。

## 手動対応が必要になりやすい典型パターン

御社の構成(ワイルドカードサブドメイン + カスタムヘッダーによるテナントルーティング)だと特に以下は要確認です。

- **ワイルドカードHost**: `*.example.local` のようなIngress側のhostルールは、HTTPRouteの `hostname` フィールドにそのまま近い形でマップされますが、Gateway側のlistener設定(前回説明した`Gateway`リソース)にもワイルドカードを明示する必要があります
- **カスタムヘッダーベースルーティング**: もしingress-nginxで `configuration-snippet` やLuaスクリプト的な独自ロジックでヘッダー判定していた場合、これはツールでは変換できません。HTTPRouteの `headers` matchで書き直すか、NGFの `SnippetsFilter` CRDで元のnginx設定スニペットをそのまま流用する形になります
- **セッションアフィニティ(cookieベース)**: `nginx.ingress.kubernetes.io/affinity: cookie` のようなセッション維持系アノテーションは、NGFのバージョンによってサポート状況が異なるため個別確認が必要です
- **TLS関連アノテーション**: `ssl-redirect` などはGateway側のリスナー設定に置き換わります

## 進め方の提案

1. `ingress2gateway` を構築用機(インターネット接続あり)で実行し、既存Ingressから変換YAMLを生成
2. 出力されたコメント(変換できなかったアノテーション)を洗い出し、御社固有のワイルドカード・ヘッダールーティングロジックと突き合わせ
3. 変換できない部分は `SnippetsFilter` CRD、もしくはHTTPRouteのネイティブ機能への書き換えで個別対応

ingress2gatewayのバイナリ自体もair-gapped環境への持ち込み(変換は構築用機側で完結するので、実はクラスタ内には不要)という位置づけになります。実際に今お持ちのIngressマニフェストを見せていただければ、どのアノテーションが自動変換されてどこが手動対応になりそうか、具体的に確認できます。
