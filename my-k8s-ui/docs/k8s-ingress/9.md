NGINX Ingress ControllerからNGINX Gateway Fabricへの移行では、単一のリソース（`Ingress`）に集中していた設定を、インフラ管理層（`Gateway`）とテナント開発層（`HTTPRoute`）の役割に基づいて分離する設計への変更が最大の違いです。

ワイルドカードサブドメインを使ったマルチテナント環境において、各役割の責任とマニフェスト構成は以下のように変わります。

---

### 主なアーキテクチャ変更点

* **責任分離 (Role-oriented API)**:
* **インフラ管理者**: ポート、TLS証明書、接続を許可するNamespaceルール（`allowedRoutes`）を持つ `Gateway` リソースを共有管理。
* **テナント管理者**: 自身のNamespace内で `HTTPRoute` リソースを作成し、各自のワイルドカードホスト（例: `*.tenant-a.example.com`）とバックエンドサービスのマッピングを定義。


* **マルチテナントセキュリティ制御**:
* `Gateway` 側の `allowedRoutes` で許可されたNamespaceからのみ `HTTPRoute` のアタッチを受け付けるため、意図しないテナントによるドメインのハイジャックを防止可能。


* **ワイルドカード指定**:
* `HTTPRoute` の `spec.hostnames` フィールドで `*.tenant-a.example.com` などのワイルドカード記法を直感的にネイティブ記述可能。



---

### 移行前後の設定比較例

#### シナリオ前提

* 共通ドメイン: `*.example.com`
* インフラ管理Namespace: `infra-system`
* テナントA Namespace: `tenant-a`（割り当てホスト: `*.tenant-a.example.com`）
* テナントB Namespace: `tenant-b`（割り当てホスト: `*.tenant-b.example.com`）

---

#### 1. 移行前：NGINX Ingress Controller

Ingressでは、各テナント用のマニフェスト内にホスト名、TLS証明書、ルーティングルール、各種Annotationを混在させて記述していました。

```yaml
# [移行前] tenant-a 内で作成していた Ingress リソース
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: tenant-a-ingress
  namespace: tenant-a
  annotations:
    kubernetes.io/ingress.class: "nginx"
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  tls:
  - hosts:
    - "*.tenant-a.example.com"
    secretName: wildcard-example-tls
  rules:
  - host: "*.tenant-a.example.com"
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: tenant-a-service
            port:
              number: 80

```

---

#### 2. 移行後：NGINX Gateway Fabric

移行後は「基盤設定」と「テナントルーティング設定」に分解して作成します。

##### Step 1: 【インフラ管理者】共通 Gateway の作成 (`infra-system` Namespace)

すべての外部トラフィックを受信するリスナーを設定し、どのNamespaceからルーティング定義の接続を許可するかを制御します。

```yaml
# [移行後] インフラ管理者が作成する共有 Gateway
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: shared-gateway
  namespace: infra-system
spec:
  gatewayClassName: nginx
  listeners:
  - name: https-wildcard
    protocol: HTTPS
    port: 443
    hostname: "*.example.com"
    tls:
      mode: Terminate
      certificateRefs:
      - name: wildcard-example-tls
        namespace: infra-system
    allowedRoutes:
      namespaces:
        from: Selector  # ラベル 'tenant: "true"' が付いたNamespaceからのアタッチを許可
        selector:
          matchLabels:
            tenant: "true"

```

##### Step 2: 【テナントA】ルーティングの設定 (`tenant-a` Namespace)

自身のNamespaceで `HTTPRoute` を作成し、`parentRefs` で共有 `shared-gateway` に紐付けます。

```yaml
# [移行後] テナントAが作成・管理する HTTPRoute
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: tenant-a-route
  namespace: tenant-a
spec:
  parentRefs:
  - name: shared-gateway
    namespace: infra-system
  hostnames:
  - "*.tenant-a.example.com"
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /
    backendRefs:
    - name: tenant-a-service
      port: 80

```

##### Step 3: 【テナントB】ルーティングの設定 (`tenant-b` Namespace)

同様に、テナントBも独立して安全にルーティングを設定可能です。

```yaml
# [移行後] テナントBが作成・管理する HTTPRoute
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: tenant-b-route
  namespace: tenant-b
spec:
  parentRefs:
  - name: shared-gateway
    namespace: infra-system
  hostnames:
  - "*.tenant-b.example.com"
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /
    backendRefs:
    - name: tenant-b-service
      port: 80

```

---

### 移行時の重要チェックポイント

* **Namespace間アクセスの許可 (`allowedRoutes`)**:
* Gateway APIの標準仕様では、Gatewayと同一のNamespaceにあるRouteのみが許可される仕組み（`Same`）になっています。
* マルチテナント化する場合は、必ず Gateway 側の `allowedRoutes.namespaces.from` を `All` または `Selector` に設定してください。


* **Annotations から Dedicated Policy への移行**:
* Ingressの `nginx.ingress.kubernetes.io/*` 注釈はそのまま利用できません。
* 代わりに NGINX Gateway Fabric が提供する CRD（例: クライアント接続設定には `ClientSettingsPolicy`、認証には `AuthenticationFilter`）や、`HTTPRoute` 内の標準 `filters` 機能を利用して同等の処理を設定します。


* **証明書の集約**:
* ワイルドカードTLS証明書（`Secret`）は `Gateway` と同じインフラ管理Namespaceに保持するのがベストプラクティスです。別Namespaceにある証明書を参照する場合は `ReferenceGrant` リソースが必要になります。


* **変換ツールの活用**:
* Kubernetes公式サブプロジェクトの `ingress2gateway`（NGINXプロバイダに対応）を使用すると、既存IngressリソースからGateway APIリソースへの初期変換マニフェストを自動出力できます。
