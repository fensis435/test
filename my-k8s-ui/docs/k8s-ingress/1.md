## 確認結果

Kubernetes Steering Committee と Security Response Committee が2026年1月29日に公式声明を出しており、2026年3月にIngress NGINXは正式に引退し、以降はバグ修正・セキュリティパッチ・いかなる更新も提供されません。現時点(2026年3月以降)ではリポジトリはアーカイブされ読み取り専用になっています。

背景としては、プロジェクトが実質1〜2名の開発者による夜間・週末対応の"生命維持"状態で運営されており、2025年のIngressNightmare脆弱性(CVE-2025-1974)がアーキテクチャ上の深刻な問題を露呈させたこと、後継として計画されていたInGateも十分に成熟せず同様に引退したことが挙げられています。

## この状況でどうするか

まだ本格構築前(EKS上での動作確認フェーズ)とのことなので、**今から新規に組むならingress-nginxは避けて最初からGateway APIベースで構築するのが得策**です。マイグレーションコストをそのままゼロにできます。

### 選択肢の比較

**① NGINX Gateway Fabric**
同じnginxエンジンをベースにしたGateway API実装で、F5社が主導し積極的にメンテナンスされています。今まで検討していたnginx-ingressのアノテーション運用からの移行コストが最も低く、on-premのnginxベース挙動に最も近い体験を維持できます。ワイルドカードHostname、カスタムヘッダーマッチングもHTTPRouteでネイティブサポートされているので、テナントルーティング要件にも合致します。

**② AWS Gateway API Controller**
AWSが提供するネイティブGateway API実装で、内部的にALBを使います。alb-controllerを既に導入済みなので親和性は高いですが、以前議論した「ALBはTLSパススルーできない」問題が再浮上します。ALBがTLS終端を担う設計に転換する前提が必要になります。

**③ Traefik**
SUSEがRancher/RKE2向けに推奨している移行先ですが、貴社スタックとの親和性は特に高くありません。

### 推奨

今回のケース(私有プライベートEKS、nginxで完結させたいワイルドカードサブドメイン+カスタムヘッダーのテナントルーティング、NLB経由でTLSパススルー)には**①NGINX Gateway Fabric**が最も自然です。これまで検討してきたNLB前段の構成(TLS終端は内部で実施、SNI/Hostヘッダーend-to-end)、Helmでの持ち込み、skopeoでのイメージ同期という流れはそのまま使えます。リソース定義がIngress→HTTPRoute/Gatewayに変わるだけで、SSMポートフォワード経由のローカルDNS動作確認の手順にも影響はありません。
