具体的なBefore/Afterで見た方が早いと思うので、御社の構成(ワイルドカードサブドメイン + ヘッダーベースのテナントルーティング)に近い例を作りました。

## Before: ingress-nginx

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: multi-tenant-ingress
  namespace: default
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/rewrite-target: /$2
    nginx.ingress.kubernetes.io/configuration-snippet: |
      if ($http_x_tenant_id = "") {
        return 400;
      }
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - "*.example.local"
      secretName: example-local-wildcard-tls
  rules:
    - host: "*.example.local"
      http:
        paths:
          - path: /api(/|$)(.*)
            pathType: ImplementationSpecific
            backend:
              service:
                name: tenant-api-svc
                port:
                  number: 8080
```

## After: Gateway API (NGF)

3つのリソースに分解されます。**Gateway**(リスナー/TLS)、**HTTPRoute**(ルーティングルール)、そして`configuration-snippet`のような素のnginx.confロジックは**SnippetsFilter**(NGF独自CRD)に対応します。

### ① Gateway(リスナー定義、インフラ管理者領域)

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: tenant-gateway
  namespace: nginx-gateway
spec:
  gatewayClassName: nginx
  listeners:
    - name: http
      port: 80
      protocol: HTTP
      hostname: "*.example.local"
    - name: https
      port: 443
      protocol: HTTPS
      hostname: "*.example.local"
      tls:
        mode: Terminate
        certificateRefs:
          - name: example-local-wildcard-tls
            namespace: nginx-gateway
```

`ssl-redirect: "true"` はこのGateway側でHTTPリスナーにリダイレクトフィルタを設定する形に変わります(HTTPRoute側でRequestRedirectフィルタとして書くのが一般的)。

### ② HTTPRoute(ルーティングルール、開発者領域)

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: tenant-api-route
  namespace: default
spec:
  parentRefs:
    - name: tenant-gateway
      namespace: nginx-gateway
  hostnames:
    - "*.example.local"
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /api
          headers:
            - name: X-Tenant-Id
              type: RegularExpression
              value: ".+"
      filters:
        - type: URLRewrite
          urlRewrite:
            path:
              type: ReplacePrefixMatch
              replacePrefixMatch: /
      backendRefs:
        - name: tenant-api-svc
          port: 8080
```

### 変換ポイント対応表

| ingress-nginxアノテーション | Gateway API/NGFでの表現 |
|---|---|
| `ssl-redirect` | HTTPリスナー側HTTPRouteの`RequestRedirect`フィルタ |
| `rewrite-target` | HTTPRouteの`URLRewrite`フィルタ(`ReplacePrefixMatch`) |
| pathの正規表現キャプチャ(`/api(/\|$)(.*)`) | `PathPrefix`マッチ + `URLRewrite`の組み合わせ(正規表現キャプチャそのものは非対応、明示的なprefix書き換えに置き換え) |
| Hostヘッダーによるテナント振り分け | `hostnames`フィールド(ワイルドカードそのままネイティブ対応) |
| カスタムヘッダー存在チェック(`X-Tenant-Id`必須) | HTTPRouteの`matches.headers`(ネイティブサポート、`configuration-snippet`の`if`文が不要に) |
| `configuration-snippet`の任意nginx.conf注入 | ネイティブ機能で表現できない場合のみ`SnippetsFilter`(NGF独自CRD)で元のnginx構文をそのまま埋め込み可能 |

### ③ もしどうしても素のnginx.conf構文が必要な場合: SnippetsFilter

ヘッダー必須チェックのような単純な条件は上記のようにHTTPRouteネイティブでカバーできますが、より複雑な`if`文や独自ロジックがあれば以下のようにエスケープハッチとして残せます。

```yaml
apiVersion: gateway.nginx.org/v1alpha1
kind: SnippetsFilter
metadata:
  name: tenant-header-check
  namespace: default
spec:
  snippets:
    - context: http.server.location
      value: |
        if ($http_x_tenant_id = "") {
          return 400;
        }
```

これをHTTPRouteの`filters`から`extensionRef`で参照する形になります。

## 重要な変化点まとめ

1. **1つのIngressが最低2つのリソース(Gateway + HTTPRoute)に分割される** → 責務分離(インフラ管理者 vs アプリ開発者)の反映
2. **path正規表現キャプチャグループは非対応** → prefixベースの書き換えへの作り直しが必要
3. **ヘッダーマッチはネイティブ機能化** → `configuration-snippet`のようなアドホックなLua/if文埋め込みが減らせる、むしろ整理のチャンス
4. **どうしても表現できない部分だけSnippetsFilterに退避** → 全部が綺麗に変換できるわけではないが、以前検討した`ingress2gateway`ツールがこのあたりの機械変換とコメント化を自動でやってくれます

もし実際にお使いのIngress manifest(アノテーション込み)を見せていただければ、この対応表に沿ってより具体的に変換例を作れます。
