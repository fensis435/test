EKS自体は Gateway API を内蔵・同梱していません(OpenShiftのように「このOCPバージョンにはこのGateway APIが標準搭載」という仕組みはEKSにはない)。したがって**バージョンを決めるのは「EKSクラスタのKubernetesバージョン」と「導入するNGFのバージョン」の掛け合わせ**になります。

## 確認する順番

### ① EKSクラスタのKubernetesバージョンを確認

```bash
kubectl version -o json | jq -r '.serverVersion.gitVersion'
# または
aws eks describe-cluster --name <cluster-name> --query "cluster.version" --output text
```

NGFの最小要件は現在Kubernetes 1.25以降です(バージョンによって上がる可能性があるのでNGF側のTechnical Specificationsも要確認)。

### ② 導入予定のNGFバージョンが要求するGateway APIバージョンを確認

NGFの公式ドキュメント「Technical specifications」ページに、NGFバージョンごとの対応表(サポートするGateway APIバージョン、対応Kubernetesバージョン範囲)が掲載されています。ここが唯一の正となる情報源です。

```
https://docs.nginx.com/nginx-gateway-fabric/overview/technical-specifications/
```

例えば、NGFはv1.1.0のGateway APIに更新した際、旧バージョン(v1.0.0)との互換性を切っています。つまりNGFのマイナーバージョンが上がるとGateway APIの必須バージョンも変わる可能性があるため、**「今使っているNGFバージョン」に対応する表の値を必ず見る**必要があります。

### ③ Gateway API CRDをその指定バージョンでpull

```bash
# Technical specificationsで確認したバージョン番号を使う(例: v1.5.1)
curl -LO https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.5.1/standard-install.yaml
```

## ハマりやすい点

- Helmチャートは**Gateway API CRDの自動インストール・自動アップグレードをしません**。CRDは必ず事前に手動でapplyしておく必要があります(前回手順の通り)。
- NGFをアップグレードする際も、HelmはNGF自身のCRDを自動更新しないので、都度GitHubからマニフェストをpullして手動適用が必要です。
- 完全プライベート環境なので、Technical Specifications表の確認・バージョン選定は**インターネット接続がある構築用機側で先に済ませておき**、決定したバージョン番号(Gateway API側・NGF側の両方)をair-gapped持ち込み用のマニフェスト取得コマンドに反映する、という順序になります。

まとめると「EKSにおけるGateway APIバージョン」という固定の答えがあるわけではなく、EKSのK8sバージョンとNGFのTechnical Specifications表を突き合わせて都度選定する、という運用になります。
