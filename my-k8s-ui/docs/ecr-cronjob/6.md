今回の専用Podは「ECRの認証情報を他Podへ配布するPod」ではなく、**EKS上でAWS APIを利用してECR OCI Helm Registryに対して `helm list / install / uninstall` を実行するPod**です。

この場合、第一候補は完全に、

> **専用Pod + EKS Pod Identity + IAM Role + ECR**

です。

                              │

                    │  Helm Operator Pod │

                    │                    │

                    │ ecr:...            │

```text

ExternalSecret
Kubernetes Secret
ECR token CronJob
```

---

# 2. なぜESO不要なのか

今回の処理は、

```bash
helm list
helm install
helm uninstall
```

ですよね。

つまり、Helmを実行するPod自身がECRへアクセスできればよい。

Pod Identityによって、

```text
Pod
 ↓
EKS Pod Identity Agent
 ↓
IAM Role
 ↓
AWS STS/EKS Auth
 ↓
ECR
```

という認証経路を作れます。

そのため、

```text
ECR password
```

をKubernetes Secretとして保存する必要がありません。

これはESOを使うよりも設計として自然です。

---

# 3. ただし `helm list` は少し注意

ここは重要です。

```bash
helm list
```

と、

```bash
helm list --registry-config ...
```

は別の話です。

**Helmのrelease情報はKubernetes側に保存されます。**

一方、

```text
oci://xxxxxxxx.dkr.ecr.ap-northeast-1.amazonaws.com/chart
```

をinstallする場合はECR Registryへの認証が必要です。

したがって、

```text
helm list
```

自体はECRアクセスを必要としません。

```text
helm install
```

のChart取得時にECRアクセスが必要です。

---

# 4. Helm install時の認証

Pod IdentityでIAM Roleを取得できるなら、専用Pod内で、

```bash
aws ecr get-login-password --region ap-northeast-1 \
  | helm registry login \
      --username AWS \
      --password-stdin \
      123456789012.dkr.ecr.ap-northeast-1.amazonaws.com
```

としてから、

```bash
helm install \
  my-release \
  oci://123456789012.dkr.ecr.ap-northeast-1.amazonaws.com/my-chart \
  --version 1.2.3
```

とできます。

重要なのは、

```text
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
```

をPodへ渡さないことです。

Pod Identityが提供します。

---

# 5. さらに「毎回helm registry login」でもよい

専用Podが短命Jobなら、むしろこれで十分です。

```text
Job開始
 ↓
Pod IdentityでIAM credential取得
 ↓
aws ecr get-login-password
 ↓
helm registry login
 ↓
helm install
 ↓
終了
```

ECR authorization tokenは12時間有効ですが、Jobごとに取得しても問題ありません。

つまり、以前のCronJobのような、

```text
6時間ごとにSecretを更新
```

という考え方そのものを捨てられます。

# 6. IAM Policy

まずECRへの権限です。

OCI Helm ChartをECRからpullするだけなら、基本的にはECRのpull系権限が必要です。

例えば、

```yaml
Statement:
  - Effect: Allow
    Action:
      - ecr:GetAuthorizationToken
    Resource: "*"

  - Effect: Allow
    Action:
      - ecr:BatchCheckLayerAvailability
      - ecr:BatchGetImage
      - ecr:GetDownloadUrlForLayer
    Resource:
      - arn:aws:ecr:ap-northeast-1:123456789012:repository/my-chart
```

です。

`GetAuthorizationToken`は`Resource: "*"`です。

# 13. Registry abstraction

例えば、

```text
interface RegistryAuthenticator {
    Login(ctx context.Context) error
}
```

AWS版：

```text
ECRAuthenticator
    ↓
aws ecr get-login-password
    ↓
helm registry login
```

オンプレ版：

```text
BasicAuthenticator
    ↓
username/password
    ↓
helm registry login
```

とします。

アプリケーションは、

```text
authenticator.Login()
helm install()
```

しか知りません。

# 14. さらに私は「AWS/オンプレ判定」をしない

ここはかなり重要です。

悪い例：

```go
if environment == "aws" {
    ecrLogin()
} else {
    harborLogin()
}
```

ではなく、

```text
registry.authenticator
```

をDIで差し替えます。

例えば設定：

### AWS

```yaml
registry:
  type: ecr
```

### On-prem

```yaml
registry:
  type: basic
```

コード：

```text
registry.type
     │
     ├── ecr   → ECRAuthenticator
     └── basic → BasicAuthenticator
```

とします。

## 結論

今回の条件なら、前回提案したESO構成は**撤回してよい**です。

特に、

> ECRへアクセスする専用Podが `helm list / helm install / helm uninstall` を行う
> EKS Pod Identityを前提とする

のであれば、

**AWS側：**

```text
Helm Operator Pod
    ↓
EKS Pod Identity
    ↓
IAM Role
    ↓
ECR
```

を第一選択にします。

**ESOは使わない。ECR tokenをKubernetes Secretにも保存しない。**

そしてAWS/オンプレ両対応については、

* **Helm valuesで環境差分を注入**
* **AWS固有のIAM/Pod IdentityはHelm Chartの外側のIaCで管理**
* **専用Pod内では`RegistryAuthenticator`という抽象化を置く**
* **AWSはECR authenticator、オンプレはBasic/Harbor authenticator**
* **アプリケーション本体には「AWSかどうか」の判定を入れない**

という構成が最もバランスがいいと思います。

なお、`helm install`を実行する専用Podについては、**Pod IdentityでECR認証する場合の「AWS SDK/CLIを使う方式」と「Helm自身のOCI credential providerにAWS credential chainを渡す方式」のどちらにするか**で、実装をさらにシンプルにできます。ここは現在使っているHelmのバージョンによって選択肢が変わるので、**Helmのバージョンを固定した上でDockerfile・Deployment・IAM CloudFormation・Pod Identity・RBAC・AWS/オンプレ両方のvalues.yamlまで一式に落とす**のが次のステップです。
