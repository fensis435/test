**CronJob方式を廃止して、EKS Pod Identity + ESO ECRAuthorizationToken Generator + Argo CD repository Secret** にするのがよいです。

以下は、元の `1.md` / `2.md` の構成を踏まえつつ、**完全Private EKS・EKS API private endpoint・管理端末からはSSM Port Forwarding経由**を前提にした実装例です。

なお、ESOのECR Generatorは `ecr:GetAuthorizationToken` を使用して12時間有効な `username/password/proxy_endpoint/expires_at` を生成できます。今回の用途にまさに対応しています。([External Secrets][1])

---

# 1. 最終構成

まず全体像です。

```text
                    管理端末
                       │
                       │ AWS SSM
                       │ Port Forwarding
                       ▼
              ┌─────────────────┐
              │ Management EC2  │
              │ private subnet  │
              │                 │
              │ kubectl / helm  │
              └────────┬────────┘
                       │
                 Private EKS API
                       │
        ┌──────────────┴──────────────┐
        │                             │
        ▼                             ▼
  ESO Controller              Argo CD Repo Server
        │                             │
        │ EKS Pod Identity            │
        ▼                             │
 EKS Pod Identity Agent              │
        │                             │
        ▼                             │
     EKS Auth                         │
        │                             │
        ▼                             │
   IAM Role                          │
        │                             │
        │ ecr:GetAuthorizationToken   │
        ▼                             │
       ECR ◄──────────────────────────┘
        │
        │ ECRAuthorizationToken
        ▼
       ESO
        │
        │ ExternalSecret
        ▼
Kubernetes Secret
  ├─ type: helm
  ├─ username: AWS
  ├─ password: <12h token>
  ├─ enableOCI: "true"
  └─ argocd.argoproj.io/secret-type: repository
```

EKS Pod Identityをprivate clusterで使う場合、**EKS Auth APIのVPC endpoint `com.amazonaws.<region>.eks-auth` が必要**です。AWSもprivate clusterでのPod Identityについて明記しています。([AWS ドキュメント][2])

# 2. 重要な前提

以下を前提にします。

```text
AWS Account
  123456789012

Region
  ap-northeast-1

EKS
  my-eks-cluster

EKS private API endpoint
  enabled

Namespace
  argocd

ESO namespace
  external-secrets

ECR repository
  my-chart

ECR registry
  123456789012.dkr.ecr.ap-northeast-1.amazonaws.com
```

また、

* EKS nodeはprivate subnet
* EKS APIはprivate only
* 管理端末からEKS APIへ直接アクセスしない
* 管理用EC2へSSM接続
* そのEC2から `kubectl` / `helm`
* ECR/STS/EKS Auth等はVPC Endpoint経由
* インターネットへの直接egressなし

という構成にします。

AWSの完全Private EKSでは、ECR API/DKR、S3、STS、EKS AuthなどのVPC endpointが必要になります。([AWS ドキュメント][3])

完全Privateなら、ここが非常に重要です。

最低限、今回の構成では以下を用意します。

| ------------ | ------------------------------------------ |

# 6. ESOのIAM Role

ESO Controller用のIAM Roleを作ります。

ここでは**ECRのToken取得だけ**を許可します。

## `eso-ecr-role.yaml`

```yaml
AWSTemplateFormatVersion: '2010-09-09'

Description: >
  IAM role for External Secrets Operator ECR Authorization Token Generator
  using EKS Pod Identity.

Parameters:

  ClusterName:
    Type: String
    Default: my-eks-cluster

Resources:

  EsoEcrTokenRole:

    Type: AWS::IAM::Role

    Properties:

      RoleName:
        !Sub '${AWS::StackName}-eso-ecr-token-role'

      AssumeRolePolicyDocument:

        Version: '2012-10-17'

        Statement:

          - Sid: EKS Pod Identity

            Effect: Allow

            Principal:
              Service:
                - pods.eks.amazonaws.com

            Action:
              - sts:AssumeRole
              - sts:TagSession

      Policies:

        - PolicyName: EcrAuthorizationToken

          PolicyDocument:

            Version: '2012-10-17'

            Statement:

              - Sid: GetEcrAuthorizationToken

                Effect: Allow

                Action:
                  - ecr:GetAuthorizationToken

                Resource: '*'

Outputs:

  EsoEcrTokenRoleArn:

    Value:
      !GetAtt EsoEcrTokenRole.Arn

    Description:
      IAM Role ARN for ESO ECR token generator
```

`ecr:GetAuthorizationToken`についてはResourceを`*`にする必要があります。

# 9. ESO Pod Identity Association

CloudFormationでこれを作ることもできます。

今回はこちらをおすすめします。

```yaml

  EsoEcrRoleArn:
    Type: String

    Type: AWS::EKS::PodIdentityAssociation
```

```text
                │
```

となります。

# 10. ESOのインストール

ESO公式ではHelm chartからインストールできます。CRDもHelmで管理できます。([External Secrets][6])

通常の環境なら、

```bash
helm repo add external-secrets \
  https://charts.external-secrets.io

helm repo update

helm upgrade --install external-secrets \
  external-secrets/external-secrets \
  --namespace external-secrets \
  --create-namespace \
  --set installCRDs=true
```

です。

ただし、**今回の「完全Private」ではこのままではダメ**です。

管理端末やEKSからインターネットへ出られないからです。

# 11. 完全PrivateでのESOインストール方法

おすすめは、

```text
Internet接続可能なBuild/Management環境
             │
             │ Helm pull
             ▼
       ESO Helm chart
             │
             │ chart + images
             ▼
      Private artifact
             │
             ▼
        Private ECR
             │
             ▼
      完全Private EKS
```

です。

つまり、**ESO Helm Chartとコンテナイメージを事前にPrivate ECR等へ持ち込む**方式です。

# 14. Management EC2からHelm install

Management EC2上で、

# 15. SSM Port Forwarding

ここが今回の運用上のポイントです。

Management EC2の、

```text
10.0.10.10
```

などをSSM管理対象にします。

EKS API endpointが例えば、

```text
https://ABCDEF.gr7.ap-northeast-1.eks.amazonaws.com
```

だったとします。

ただし、EKS private endpointは通常のVPC Endpointではありません。EKSはprivate API endpointを有効にするとVPC内からAPIへアクセスできるようにします。([AWS ドキュメント][7])

# 16. SSMでManagement EC2へPort Forward

ここは注意点があります。

単純に、

```bash
aws ssm start-session
```

するだけでは、ローカルPCの`kubectl`がEKS private endpointへ到達できません。

そこで、

```text
Local PC
   │
   │ localhost:6443
   ▼
SSM
   │
   ▼
Management EC2
   │
   │ :443
   ▼
EKS Private API
```

というトンネルを作ります。

# 17. SSM Port Forward用Document

例えば、

```json
{
  "schemaVersion": "1.0",
  "description": "Port forwarding to EKS private endpoint",
  "sessionType": "Standard_Stream",
  "parameters": {
    "host": {
      "type": "String",
      "description": "Target host"
    },
    "portNumber": {
      "type": "String",
      "default": "443"
    },
    "localPortNumber": {
      "type": "String",
      "default": "6443"
    }
  },
  "properties": {
    "portNumber": "{{ portNumber }}",
    "localPortNumber": "{{ localPortNumber }}",
    "host": "{{ host }}"
  }
}
```

というSession Manager documentを用意します。

あるいはAWS Systems Manager標準のポートフォワーディング機能を使います。

# 21. ECRAuthorizationToken Generator

今回の中心部分です。

```yaml
apiVersion: generators.external-secrets.io/v1alpha1
kind: ECRAuthorizationToken

metadata:
  name: ecr-authorization-token
  namespace: argocd

spec:

  region: ap-northeast-1

  scope: private
```

ECR Generatorの`scope`にはprivate/publicがあり、今回のECRはprivateなので`private`を指定します。([External Secrets][8])

---

# 22. SecretStore

今回、ECR GeneratorそのものはAWS SDKのdefault credential chainからESO ControllerのPod Identityを利用します。

したがって、**SecretStoreにAWS access keyを持たせません。**

例えば：

```yaml
apiVersion: external-secrets.io/v1
kind: SecretStore

metadata:
  name: aws-ecr
  namespace: argocd

spec:

  provider:

    aws:

      service: ECR

      region: ap-northeast-1
```

ただし、今回のECR Generatorは`SecretStore`を直接使うのではなく、GeneratorとしてAWS APIを呼びます。

そのため、実際には**このSecretStoreは必須ではありません**。

---

# 23. ここは設計上整理した方がよい

今回、

> 「SecretStore/ClusterSecretStore + ExternalSecret」

も指定されていますが、ECR Token Generatorを使う場合、

```text
ECRAuthorizationToken
        ↓
ExternalSecret
```

だけで成立します。

つまり、

```text
SecretStore
```

は今回のECR token取得には不要です。

これはESOのGenerator仕様によるものです。ExternalSecretは`dataFrom.sourceRef.generatorRef`でGeneratorを直接参照できます。([External Secrets][9])

なので、**無理にSecretStoreを挟まない方が構成がシンプル**です。

---

# 24. それでもSecretStoreを用意するなら

将来的に、

```text
AWS Secrets Manager
SSM Parameter Store
ECR
```

などをESOで扱う予定があるなら、ClusterSecretStoreを用意しておくのは合理的です。

例えば：

```yaml
apiVersion: external-secrets.io/v1
kind: ClusterSecretStore

metadata:
  name: aws-private

spec:

  provider:

    aws:

      service: SecretsManager

      region: ap-northeast-1
```

Pod Identity利用時は、ESO公式の説明どおり、ここに`auth.serviceAccountRef`を指定しません。([External Secrets][5])

# 25. ExternalSecret

ここがArgo CDとの接続部分です。

```yaml
apiVersion: external-secrets.io/v1
kind: ExternalSecret

metadata:
  name: ecr-helm-repo-secret
  namespace: argocd

spec:

  refreshInterval: 6h

  target:

    name: ecr-helm-repo-secret

    creationPolicy: Owner

    template:

      type: Opaque

      metadata:

        labels:
          argocd.argoproj.io/secret-type: repository

      data:

        type: helm

        name: ecr-helm-repo

        url: "123456789012.dkr.ecr.ap-northeast-1.amazonaws.com"

        enableOCI: "true"

        username: "{{ .username }}"

        password: "{{ .password }}"

  dataFrom:

    - sourceRef:

        generatorRef:

          apiVersion: generators.external-secrets.io/v1alpha1

          kind: ECRAuthorizationToken

          name: ecr-authorization-token
```

ESOのECR Generatorは`username`、`password`、`proxy_endpoint`、`expires_at`を出力するため、`username/password`をそのままArgo CD repository Secretにテンプレートできます。([External Secrets][1])

# 26. これで生成されるSecret

最終的にKubernetesには概念的に、

```yaml
apiVersion: v1
kind: Secret

metadata:
  name: ecr-helm-repo-secret
  namespace: argocd

  labels:
    argocd.argoproj.io/secret-type: repository

type: Opaque

stringData:
  type: helm
  name: ecr-helm-repo
  url: 123456789012.dkr.ecr.ap-northeast-1.amazonaws.com
  enableOCI: "true"
  username: AWS
  password: <ECR-TOKEN>
```

が存在します。

Argo CDのOCI Helm repository Secretでは、`type: helm`と`enableOCI: "true"`を設定する構成が公式ドキュメントにあります。([Argo CD][10])

---

# 28. 重要：`refreshInterval: 6h`

ここは元のCronJobの、

```yaml
schedule: "0 */6 * * *"
```

を置き換える部分です。

ECR tokenは12時間有効です。([External Secrets][1])

したがって、

```yaml
refreshInterval: 6h
```

で、

```text
0h     token A
6h     token B
12h    token C
18h    token D
```

という運用になります。

---

# 29. もう少し安全側にするなら `1h`

例えば、

```yaml
refreshInterval: 1h
```

でも構いません。

ECRのToken APIを毎時呼ぶ程度なら、今回の用途では通常問題になりにくいです。

ただし、

```text
12h token
6h refresh
```

で十分な余裕があります。

私は、

```yaml
refreshInterval: 6h
```

を採用します。

---

# 30. `SecretStore`と`ClusterSecretStore`のどちらを使うか

今回なら、

### ECR Tokenだけ

```text
ECRAuthorizationToken
       ↓
ExternalSecret
```

なのでSecretStore不要。

### 将来的にAWS Secrets Manager等もESOで使う

```text
ClusterSecretStore
       ↓
ExternalSecret
```

をおすすめします。

理由は、AWS credential取得の共通設定をClusterSecretStoreとして一元化できるからです。

ただしECR Generatorについては、**ClusterSecretStoreを経由させるために複雑化しない方がいい**です。

# 34. ここで一つ重要な改善

元の構成では、

```text
ACCOUNT_ID
REGION
```

をCronJobのshellで組み立てていました。

ESO版ではこれをやめて、

```yaml
url: "123456789012.dkr.ecr.ap-northeast-1.amazonaws.com"
```

のように**固定値としてGit管理する**のをおすすめします。

これはSecretではありません。

ECRのrepository URLは機密情報ではないためです。

# 38. 完全Privateでのネットワーク要件


も必要です。AWSの完全Private EKSでもこのECR API/DKR + S3構成が示されています。([AWS ドキュメント][3])

このSecretは、


```text

 │
 ├─ ECRAuthorizationToken

          │

          │
          ▼
```

という関係にします。

# 48. つまりArgo CD自身で管理する場合

ここはBootstrap時に注意が必要です。

ESOがまだ存在しない状態で、

```text
ExternalSecret
```

だけArgo CDからapplyしてもSecretは作られません。

したがって初回Bootstrapは、

```text
1. EKS
2. Pod Identity Agent
3. ESO
4. IAM Pod Identity Association
5. ECRAuthorizationToken
6. ExternalSecret
7. Argo CD repository Secret生成
8. Argo CD Application
```

の順序が安全です。

# 51. 最終的なIAM権限

今回、ESO Controllerに与えるIAM権限は基本的に、

```yaml
Action:
  - ecr:GetAuthorizationToken
Resource: "*"
```

だけです。

かなり綺麗です。

ESOがKubernetes Secretを作成するための権限は、AWS IAMではなく**Kubernetes RBAC**としてESO Controllerにあります。

つまり、

```text
AWS IAM
  └─ ECR token取得

Kubernetes RBAC
  └─ Secret作成/更新

ESO
  └─ 両者をつなぐ
```

という責務分離になります。

**今回なら、これを完成形とします。**

```text
                    AWS VPC
┌───────────────────────────────────────────────┐
│                                               │
│  Management EC2                               │
│       ▲                                       │
│       │ SSM                                   │

│  │       │ Pod Identity                  │    │
│  │       ▼                               │    │
│  │  EKS Pod Identity Agent               │    │
│  │       │                               │    │
│  │       ▼                               │    │
│  │  EKS Auth Endpoint                    │    │
│  │       │                               │    │
│  │       ▼                               │    │
│  │  IAM Role                             │    │
│  │       │                               │    │
│  │       │ ecr:GetAuthorizationToken     │    │
│  │       ▼                               │    │

│  │       ▼                               │    │

│                                               │
```

この構成なら、元のファイルで問題だった**CronJob、初回実行、`kubectl`動的ダウンロード、AWS CLIイメージ、Secret更新処理の自前実装**をまとめて排除できます。一方、ECR Tokenの12時間という制約はESOがそのまま吸収します。([External Secrets][1])

なお、**「完全Private」の意味を「EKSだけprivateで、Management EC2はSSM経由、ただしNAT Gatewayによる外向き通信は許可」ではなく、「NAT GatewayすらなくAWS API/コンテナレジストリも全てVPC Endpointのみ」まで厳密にする場合、ESOのイメージ取得・Helm chart持ち込み・EKS add-on更新まで含めて別途Bootstrap設計が必要**です。AWSも完全Private EKSではAWSサービスごとのVPC Endpointを構成する方式を示しています。([AWS ドキュメント][3])

その前提なら、**次に作るべきものは「この構成をそのままGitに置けるファイル一式」**です。具体的には `01-vpc-endpoints.yaml`、`02-eso-iam.yaml`、`03-eso-pod-identity.yaml`、`04-eso-install-values.yaml`、`05-ecr-generator.yaml`、`06-externalsecret.yaml`、`07-argocd-application.yaml` と、**SSM Port Forwarding用のIAM Policy / Session Manager設定 / Management EC2構築手順まで含めたBootstrap手順書**にすると、そのまま構築手順として使える形になります。
