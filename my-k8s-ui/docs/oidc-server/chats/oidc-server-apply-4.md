### なぜ「起動スクリプトで`.env`を書き換える」だけでは不十分か

Viteの`import.meta.env.VITE_*`は**`vite build`実行時点で、値がJavaScriptファイルの中に文字列としてそのまま埋め込まれます**(実行時に環境変数を読みにいく仕組みではありません)。

```js
// ビルド後の実際のJSファイルの中身(イメージ)
const issuer = "https://idp.dev.test";  // ← ビルド時の値がハードコードされている
```

そのため、コンテナ起動時に`.env`を書き換えても、**それより前に(CIのDockerイメージビルド時に)`vite build`が終わっている限り、書き換えは一切反映されません**。反映させるには、コンテナ起動のたびに`.env`書き換え→`vite build`を再実行する必要がありますが、これには次の問題があります。

- Pod起動のたびにビルド時間がかかる(オートスケール時の起動遅延に直結)
- **ランタイムのコンテナイメージにNode.jsとフロントエンドのソース一式が必要になる**(「実行時はRailsしか動かさない」という現在の運用方針と矛盾する)
- 「1つのイメージを全環境で使い回す」というコンテナのベストプラクティスが崩れ、環境ごとにビルドが必要になる

### 推奨:ランタイム設定注入パターン(SPAの定石)

## 1. HMR節の簡素化
`vite dev`は使わない前提に合わせ、`LOCAL_HTTPS_SETUP.md`のCaddy設定を単純なリバースプロキシに変更しました。WebSocket周りの考慮が不要になった分、構成もシンプルになります。

## 2. ランタイム設定注入パターンへの変更(実装・検証済み)

「起動スクリプトで`.env`を書き換える」案には、**Viteが`import.meta.env.VITE_*`をビルド時にJSへハードコードしてしまう**という根本的な制約があり、そのままでは機能しません(コンテナ起動時の書き換えが、その前に完了しているビルドに反映されない)。

代わりに`window.__APP_CONFIG__` + `config.js`(コンテナ起動時にシェルスクリプトで動的生成)という、SPAの定石パターンに書き換えました。

- `runtime-config.ts`(新規): `window.__APP_CONFIG__`優先、ローカル開発時は`import.meta.env`にフォールバック
- `auth.ts` / `App.tsx`: 参照元を`getRuntimeConfig()`経由に変更
- `docker/generate-config.sh`(新規): 環境変数から`config.js`を生成するシェルスクリプト(Node.js不要)
- `docker/values-example.yaml`(新規): Helm values側のサンプル

**実際に`npm run build`を実行し、型エラー・ビルドエラーがないことを確認済みです。** また`generate-config.sh`単体でも実行し、必須環境変数のバリデーションと`config.js`の正常生成の両方を確認しました。これにより「1回ビルドしたDockerイメージを、Helm values.yamlの切り替えだけでdev/staging/本番すべてに使い回せる」ようになり、実行時のNode.js不要という運用方針とも矛盾しません。

## 3. リモートLAN(踏み台)からのアクセス(`REMOTE_LAN_ACCESS.md`新規作成)

バインド設定・DNS解決・証明書信頼配布・ファイアウォールの4点を整理しました。特に、これまでの会話に出てきたAWS SSM経由のbastion運用と発想が近い**SSHポートフォワーディング案**も代替案として用意しています。踏み台自体のブラウザで操作する場合はこちらの方がシンプルです(HTTPS化そのものが不要になります)。一方、Windows端末等**踏み台とは別の端末**からブラウザでアクセスする場合は、secure context の制約上HTTPS化(mkcert方式)が必須になる、という判断基準も明記しました。
