# Staff Engineerレビュー: 3年後の保守を前提とした設計上の欠陥

結論から言います。**このコードベースは「動く」レベルには達していますが、3年間本番で保守され続けることを想定した設計にはなっていません**。個別のバグではなく、今この段階で直さなければ後から直せなくなる「構造的決定」が複数残っています。以下、優先度の高い順に列挙します。

---

## 1. SQLiteが「開発用」から「実質本番」へすり替わっている

最初の要求は「開発用OIDC Server」でした。しかし今のこのリポジトリを見ると、Client CRUD、Webhook配信、管理者認証、K8s Ingress、NetworkPolicy、PDBまで揃っています。これはもう「開発用サーバー」の設計ではなく、**「SQLiteを使う本番相当のIdP」**です。誰もこの位置づけの変化を意思決定として明文化していません。

3年後、このサーバーは間違いなく「一時的に動かしているだけ」のはずが本番トラフィックを受けている状態になります。そのとき初めて「SQLiteだから複数レプリカにできない」という制約に気づき、緊急でPostgres移行プロジェクトが立ち上がります。**今このタイミングで「これは本番システムなのか、本当に使い捨てなのか」を意思決定し、記録すべきです。**

## 2. `OidcGenericStore`は3年後に誰も中身を説明できないブラックボックスになる

`Session`, `Interaction`, `Grant`, `DeviceCode`等をすべて`(modelName, key) -> JSON文字列`の汎用KVテーブルに突っ込む設計は、実装コストを下げる代わりに**スキーマの表現力を完全に放棄しています**。

- Prismaの型システムの恩恵を一切受けられない(すべて`unknown`→`JSON.parse`)
- oidc-providerのマイナーバージョンアップでpayloadの形が変わっても、DB層は何も検知できない
- このテーブルに対してまともなマイグレーションが書けない(中身が構造化されていないため)

3年後、oidc-providerをアップグレードした瞬間にこのテーブルの中身が読めなくなる、という障害が起きても不思議ではありません。**サードパーティOIDCライブラリの内部実装に対する防腐層(Anti-Corruption Layer)が存在しない**、というのが正確な言い方です。Cognitoに対しては執拗なまでに防腐層を用意したのに、oidc-provider自体(これも単なる一npmパッケージであり、3年間同じ依存を保証する根拠は何もない)に対しては無防備という**非対称な設計**になっています。

## 3. Cognito隔離の仕組みは「コメントで書いてあるだけ」で強制力がゼロ

`cognito-compat/claims-mapper.ts`はコードベースのどこからも呼ばれていません。「Cognito固有知識はここにしか置かない」というルールは、**コンパイラにもCIにも守らせていない、口約束**です。

最優先要件は「Cognito切替時のReact/Railsのコード変更最小化」でした。それを担保するはずの唯一の仕組みが、3年間・複数人の引き継ぎを経ても機能し続けると期待するのは楽観的すぎます。加えて、**クレーム契約(`groups`等の中立命名)が実際に守られているかを検証する契約テスト(Discoveryドキュメントの形状、Claims形状、Token形式をpinするテスト)が一つも存在しません**。これは「テストが足りない」という枝葉の指摘ではなく、**このプロジェクトの最優先要件そのものを保証する仕組みが存在しない**という核心的な欠陥です。

## 4. OIDC CoreとManagement APIが「一つのプロセス・一つのDB・一つのリポジトリ」に同居している

エンドユーザー認証(PKCE, JWT, Cognito本番に1:1対応する領域)と、管理者向けCRUD API(Cognitoには存在しない、独自の寿命を持つ領域)は、**性質もライフサイクルも信頼境界も全く異なる2つの製品**です。それが今、フォルダ分けという「紳士協定」だけで一つのExpressアプリに同居しています。

3年間・複数人が触れば、この境界は必ず溶けます。「ついでだからここに機能を足そう」が積み重なり、5年目には「なぜOIDC CoreがManagement APIのモジュールをimportしているのか誰も説明できない」状態になります。**プロセス分離、最低でもモジュール境界の強制(lintルールやパッケージ境界)が今のうちに必要です。**

さらに深刻なのは、**「Management APIはRailsからしか呼ばれない」という信頼境界が、アプリケーションコードのどこにも強制されていない**点です。唯一の防御はK8sのIngressパスとNetworkPolicyという**インフラ層の設定だけ**であり、多層防御になっていません。誰かが検証用にNodePortを一時的に開けて忘れる、Service Meshを導入してNetworkPolicyの前提が崩れる——それだけでこのシステム全体の権限モデルが無効化されます。

## 5. マルチテナント設計が存在しない(メモリの前提と矛盾している)

これまでの会話の文脈では、このIdPは「EKSベースのマルチテナント基盤」上で使われる想定です。しかし`Users`, `Groups`, `Clients`のスキーマはフラットな単一テナント設計であり、`tenant_id`はどこにも存在しません。

これは「後から`tenant_id`カラムを1本足せばいい」という話ではありません。生きているトークン・生きているセッション・生きているRefreshTokenが存在する状態で、テナント境界を全テーブルに後付けするのは、**このシステムの3年間の歴史の中で最もリスクの高いマイグレーション**になります。今この設計段階で(たとえ現状はシングルテナント固定値でも)スキーマに存在させておくべきでした。

## 6. Webhook配信に永続化保証がない(Outboxパターンの欠如)

`User`の作成はDBトランザクションでコミットされますが、そのあとの`publishUserLifecycleEvent`はawaitされない fire-and-forget です。この間にプロセスが落ちれば(デプロイ時のSIGTERM、OOM Kill等)、**「Webhookが送られるはずだった」という記録すら残らずにイベントが消えます**。

これは「配信が失敗したらリトライする」というレベルの話ではなく、**「そもそも配信を試みたことがDBに記録されない」という構造上の欠陥**です。正しくは、Userの作成と同一トランザクション内で「配信予定イベント」の行を書き込み、別プロセス(worker/cron)がそれを読んで配信するOutboxパターンにすべきでした。3年間運用すれば、この欠陥は「なぜかたまにRails側にユーザー作成が伝播しない」という、再現困難な問い合わせとして定期的に浮上します。

## 7. Management APIに冪等性の設計がない

`createUser`, `createClient`, パスワードリセットトークン発行は、Rails側からHTTP経由で呼ばれる以上、タイムアウト・リトライの対象になります。しかしどのエンドポイントにも冪等キーの仕組みがありません。

3年後、「Railsがタイムアウトしてリトライしたら、同じメールアドレスのユーザーが二重に作られかけて409で失敗した」程度ならまだいいですが、`clients/:clientId/secret/rotate`のような**副作用の大きい操作でリトライが二重発火した場合の挙動が未定義**なのは危険です。これは今のうちに設計しておくべき項目です。

## 8. 監査証跡(`createdByType`/`createdById`)が構造的にクエリ不能

FKを張らない緩い参照として設計した意図は理解できますが、これは「誰が何を作成したか」という**将来ほぼ確実に聞かれる質問(セキュリティ監査、SOC2的な統制要件)に答えられない**設計です。インデックスもなく、JOIN対象も型付けされていません。認証基盤である以上、監査ログの構造化は「あったら良い」ではなく必須要件です。3年後にコンプライアンス対応で泣くのはこの部分です。

## 9. 鍵・シークレットのローテーション設計が皆無

JWKS署名鍵、管理者JWTシークレット、Cookieキー——**このシステムの信頼の根幹をなすすべての鍵に、ローテーション手順(新旧鍵の並行有効期間、ロールオーバー中のトークン検証継続)が一切設計されていません**。K8s Secretのテンプレートに`REPLACE_ME`と書いてあるだけです。

IdPというプロダクトにとって、鍵ローテーションは機能要件の枝葉ではなく**存在理由そのものに関わる要件**です。3年間一度も鍵をローテートしない前提で運用され続けるシステムなど存在しません。

## 10. テストのリスク配分が完全に逆転している

現状のテストは「ページネーションの計算」と「URLバリデーション」という、**このシステムの中で最もリスクの低い部分**をカバーしています。一方、Authorization Code + PKCEのフロー、Refresh Tokenローテーション、Access Token検証という**最も壊れたときの被害が大きい部分(認証バイパスに直結する)には一切のテストがありません**。

これは「テストが足りない」のではなく、**「何をテストすべきかという優先順位付けの設計」が存在しない**ということです。3年間の間に必ず誰かがoidc-providerの設定を触り、誰も気づかないまま認証バイパスが混入します。

## 11. Actor(操作者)をservice関数に手渡しで運搬するパターンがスケールしない

`actor: { type, id }`を各service関数に引数として毎回渡す設計は、今は5関数だから成立していますが、コンパイラは「この関数は監査情報を記録し忘れている」ことを検知できません。3年後・50エンドポイント後には、確実に一部の操作が監査記録なしで実行される状態になります。リクエストスコープのコンテキスト(AsyncLocalStorage等)による強制か、最低限「actor引数のない書き込み操作はlintエラー」という機構が必要です。

## 12. 意思決定がコードコメントとチャット履歴にしか存在しない

このリポジトリには「なぜAuthorizationCodeはS256のみか」「なぜWebhookLogにFKがないか」という重要な設計判断が大量にありますが、それらはすべて**コードコメントの中、あるいはこの会話の中にしか存在しません**。ADR(Architecture Decision Record)としてリポジトリに永続化されたものは一つもありません。

コードコメントはリファクタリングのたびに気軽に消されます。チャット履歴は誰も後から参照しません。3年後、最初の設計者が全員いなくなった状態で「なぜこうなっているのか」を誰も説明できなくなります。**これは技術的負債ではなく、組織記憶の喪失という設計プロセス上の欠陥**です。

---

## 総括

個々の実装バグは直せます。しかし上記12項目のほとんどは、**「今この設計判断をしなかったこと」自体が3年後のコストになる種類の問題**です。特に以下の3つは、今すぐ意思決定すべき最優先事項だと考えます。

1. **このシステムは本番か使い捨てか**(SQLiteの是非を含む、根本的な位置づけの決定)
2. **Cognito隔離を「コメント」から「コンパイラ・CIが強制する仕組み」に変える**(最優先要件そのものの担保)
3. **マルチテナント境界を今スキーマに入れる**(後付けは事実上不可能に近い)

これらを先送りにするコストは、3年という時間軸では複利的に増大します。
